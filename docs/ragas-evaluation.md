# Ragas による自動評価（任意・開発用）

Issue #45。`tools/ragas_readability.py` は、推敲候補を原文と照合して Ragas で採点する開発用CLIです。既存の標準ライブラリだけの手動・表層検証は変えません。Ragas は評価基盤であり、日本語の推敲品質を検証済みの指標ではありません。**人手確認済みの日本語ケースで評価器の有効性を調べるまで、採用する指標は確定していません。**

## 導入

Ragas は任意の依存です。スキルの配布物、通常のオフライン処理、CI には含めません。専用の仮想環境に入れます。

```bash
python3 -m venv .venv-ragas
.venv-ragas/bin/python -m pip install -r tools/requirements-ragas.txt -c tools/ragas-constraints.txt
.venv-ragas/bin/python tools/ragas_readability.py check
```

`check` は通信せず、Ragas・固定版・Claude CLI の有無と、Ragas を import できるかを調べます。

### 固定した版

| 項目 | 内容 |
|---|---|
| `ragas` | 0.4.3（PyPI の最新、Apache-2.0、Python 3.9 以上） |
| `langchain-community` | **0.3.31 に固定**。0.4.2 だと `import ragas` が `ModuleNotFoundError: langchain_community.chat_models.vertexai` で失敗する（依存を最新で解決すると起こる） |
| 解決版の記録 | `tools/ragas-constraints.txt`（約90パッケージ） |
| 動作を確認した環境 | Linux、Python 3.13.16。macOS（Python 3.13.16）でも導入と実行を確認した（2026-10-17）。Python 3.15 は試していない |

依存は `langchain`、`openai`、`datasets` など多く、必須化しない判断の根拠です。

### 使う API と使わない API

Ragas 0.4.3 の公式 docs は、同じページに旧APIと現行APIが混在しています。現行のものだけを使います。

| 使う（現行） | 使わない（旧） |
|---|---|
| `ragas.metrics.collections.FactualCorrectness`、`await metric.ascore(response=, reference=)` | `SingleTurnSample`、`single_turn_ascore` |
| `ragas.metrics.DiscreteMetric`（項目別rubric、日本語プロンプトを自作） | `AspectCritic`。`ragas.metrics` からの import は非推奨で、警告が案内する `collections` 側にも 0.4.3 には存在しない |

## 実行

```bash
# 準備のみ。本文は送信せず、送信範囲と呼出し数の上限を表示して plan.json に保存する
.venv-ragas/bin/python tools/ragas_readability.py score --input evals/ragas-calibration/artificial-cases.json --out-dir /tmp/jre-ragas
# Claude CLI へ送信して採点する
.venv-ragas/bin/python tools/ragas_readability.py score --input evals/ragas-calibration/artificial-cases.json --out-dir /tmp/jre-ragas-run --execute
```

- 観点の弁別の試験として `--discriminate` を付けると、rubric の各観点に「他の観点の違いはこの観点では pass、引用できなければ pass」の指示を加えます（既定は加えません）。rubric のハッシュと設定に記録され、指示の有無が違う run は統合しません。
- 同じケースの繰り返し採点のばらつきは、通信なしの `stability` で数えます。`--repeat` を2回以上指定し、1回分の分割実行は同じ `--repeat` にまとめます。

  ```bash
  .venv-ragas/bin/python tools/ragas_readability.py stability --repeat run1-part{1,2,3}.json --repeat run2-part{1,2,3}.json --labels labels.json --out-dir NEW_DIR
  ```
- 入力は `review_readability.py` と同じ cases JSON（モードBのみ）です。ID・入力ハッシュ・原文／候補／依頼／文脈／対象読者の検査を再利用します。
- `--execute` を付けない限り、どこにも送信しません。**`--execute` は依頼・資料・原文・候補・対象読者を Claude CLI へ送信し、利用枠を消費します。**
- 評価器 LLM は、既存の `evaluate_readability.py` と同じ Claude CLI（sonnet / medium、ツールなし）をアダプタで接続します。API キーは不要です。アダプタは JSON スキーマの指示をプロンプト末尾に付け、逐次実行し、同一プロンプトは再利用します。Ragas 本来の構造化出力経路（instructor）は通りません。
- 出力先は新規ディレクトリのみで、上書きしません。終了コードは `0=完了`、`1=採点に失敗あり`、`2=入力・環境・保存エラー`。

## 採点の内容

| 区分 | 内容 | 状態 |
|---|---|---|
| FactualCorrectness（precision／recall） | response＝候補、reference＝原文。原文との整合であり、世界の事実の真偽ではない | 候補。校正前 |
| 日本語rubric（`--metrics rubric`） | 否定・条件・主体・義務の強さ・数値・原文にない具体化・不要な変更・論旨と語り口を、観点ごとに `pass/fail/uncertain` と引用付きの理由で判定する。観点の組は `--profile`（`core`、`gov-org`、`tech`、`essay`、`all`）で選ぶ | 暫定。校正後に確定する |
| 読みやすさ（`--metrics readability`） | 意味保持と分けて `better/same/worse/uncertain`。短文や低い漢字率だけを高評価にしない | 暫定 |
| Faithfulness | 未実装。precision との重複と費用を比べ、不要なら採用しない | 校正後に判断 |
| jReadability | 未確認。学習者向けの補助候補で、用途・辞書・利用条件を確認してから採否を決める | 未着手 |
| 保護対象（コード・API・数値・URL・モードC） | 既存の機械検査を使う。LLM採点で代替しない | 既存 |
| 実理解 | 既存の人手理解問題を使う。モデルのQA正答を人の理解度として報告しない | 既存 |
| 検索用指標、参照文なしの BLEU/ROUGE/SARI、埋込み類似度のみの合否 | 主要指標に採用しない | 方針 |

### FactualCorrectness の扱い

- **主張抽出は `atomicity=high`、`coverage=high` を既定にします。** Ragas の既定は `low/low` で、`coverage=low` の例は細部を意図的に落とします（docs の例では「food critic」が落ちる）。条件・例外の脱落を見たい本用途では不利と考えた**仮説**です。34件の人工例で比べた結果、この仮説は支持されませんでした（[追加の検証](#追加の検証2026-10-17)）。
- precision は候補の主張のうち原文に支持される割合、recall は Ragas の式では `TP/(TP+FN)` で、TP は**候補の主張**のうち原文に支持されるものの数です。「原文の主張のうち候補が支持する割合」ではありません。後者は `reference_claims.coverage` として別に保存します。F1 だけで報告しません。
- 主張を1件も抽出できないと、Ragas は NLI を呼ばず**黙って 0.0 を返します**。本ツールはこれを `no_claims`（値なし）として分け、0点にしません。
- 主張・判定は LLM 呼出しのログから再構成し、再計算した値が Ragas の値と一致するか（`consistent`）を記録します。一致しなければ警告します。
- 候補にあり原文で支持されない主張（追加・矛盾）と、原文にあり候補で支持されない主張（欠落）を、理由付きで保存します。
- Ragas の主張抽出・NLI のプロンプトは英語の指示と英語の例です。日本語への適合は未検証で、プロンプトを日本語へ翻訳しても適合したことにはなりません。

## 記録されるもの

出力先に `tasks.json`（入力）、`plan.json`、`ragas-run.json`、`ragas-run.md`、`raw/`（呼出しごとの生応答）を保存します。

- 設定: Ragas とその依存の版、Python、OS、Claude CLI の版とフラグ、主張抽出設定、rubric の版とハッシュ、使った観点。温度・乱数種は CLI から指定できないため「不明」と記録します。
- 呼出しごと: プロンプトのハッシュ、モデル識別子、生応答のファイル、再利用の有無、所要時間、費用（定価換算）、失敗。CLI は `claude-sonnet-5-5` と `claude-haiku-5-5` の両方を報告することがあり、そのまま記録します。
- ケースごと: 主張数、支持／不支持の主張、観点別の値と理由、失敗。
- 失敗・主張なし・判断不能は、0点や合格に変換しません。`ragas-run.md` は値の記録で、合否や総合点ではありません。

## 検証結果（2026-10-16）

#40 のデジタル庁文書群のうち**調整用側の出典だけ**を使いました。最終評価用の抜粋は使っていません。設定は `atomicity=high`、`coverage=high`、`--profile gov-org`（7観点）、評価器は Claude CLI（`claude-sonnet-5-5` と `claude-haiku-5-5` が報告される）です。記録は [`evals/ragas-calibration/results-2026-10-16/`](../evals/ragas-calibration/results-2026-10-16/README.md) にあります。

### A. 人工13件（構成ラベル）

既知の欠陥を構成した8件と、無変更の対照・正当な言い換え5件を採点しました（169呼出し、再利用38、失敗0、定価換算で約1.46 USD）。判定規則は結果を見る前に固定しています（ただし先行のスモーク3件は見たあとです）。

| 指標 | 欠陥あり（8件） | 欠陥なし（5件） |
|---|---|---|
| factual の信号（precision／recall のどちらかが 1.0 未満） | 8/8 | 1/5 |
| rubric の信号（不要な変更を除く保持の観点のいずれかが fail） | 8/8 | 0/5 |
| 違反した観点が fail | 8/8 | — |
| 不要な変更が fail | 8/8 | 0/5 |

読み取れること（人の確認前の構成ラベル、13件、出典2文書の範囲）:

- 構成した欠陥は露骨で、検出できて当然の水準です。この表は、評価器が**明らかな欠陥を見逃さない**ことの最低限の確認にとどまり、微妙な改変への有効性は示しません。
- 欠陥なしの偽警告は factual で1件でした（`paraphrase-s6`、precision 0.75）。主張抽出が「留意してください」を「留意すべきである」という主張に変え、NLI が支持されないと判定したためで、言い換えの副産物です。
- **rubric は観点を弁別していません。** 欠陥1件あたり fail になった観点数は `[3, 5, 6, 3, 4, 4, 5, 4]` で、狙った観点だけが fail になった例はありません。同じ理由文が複数の観点に繰り返されます。「どの観点が壊れたか」の判定には使えず、「何か壊れている」の信号として読むのが妥当です。
- factual の信号は、私の読みでは8件中7件で**正しい理由**でした。欠落・追加・変更された主張そのものが列挙されます（例: 例外の脱落では「情報システムの監視は24時間365日行うこと」が原文側の不支持主張に、原文にない確定表現の追加では「追加のコストが必ず発生する」が候補側の不支持主張に出る）。人が確認するときの根拠として有用です。
- 残る1件（`strength-s3b`、「提案すること」→「提案することが望ましい」）は、**別の理由で信号が出ました**。本実行では recall が 1.0 で欠陥を拾えず、precision が「連絡体制が存在する」という主張で下がっただけです。スモーク実行では同じケースで recall 0.67 となり、欠陥（提案が求められること）を拾いました。**同一ケースでも run 間でばらつきます**。繰り返し実行による分散は未測定です。
- 無変更の対照2件（`control-s3a`、`control-s6`）は全指標が満点・全観点 pass でした。正当な言い換え3件のうち、偽警告は上記の1件だけです。

### B. スキルの実生成9件（#40 調整用3抜粋×3回、ラベルなし）

スキル（コミット `0ed2a2f` 時点）で生成し、既存の `evaluate_readability.py` のLLM採点と Ragas を同じ候補に適用しました。人手のラベルはないため、**どちらが正しいかは判定していません**。

| | 件数 |
|---|---|
| 既存のLLM採点が pass | 9/9（管理対照2件は正答） |
| Ragas の信号なし（precision・recall が 1.0、保持の観点が全て pass） | 7/9 |
| Ragas の信号あり | 2/9 |

信号のあった2件はいずれも未解決で、確定した不具合ではありません。

- `g002`（recall 0.75）: 原文の「政策目的…等の観点を**主眼として**優先順位を判断していきます」を、候補は「**主な判断材料として**…判断します」に変えました。NLI は「主眼とするとは述べられていない」と判断しました。微妙な意味のずれの可能性があり、既存のLLM採点は見逃した（または許容した）ことになります。**人の判断が必要**です。
- `g001`（rubric の `condition_scope` が fail）: その理由文は「条件・範囲の脱落や変更はない」と書いており、**値（fail）と理由が矛盾**しています。rubric の出力の信頼性の問題で、偽警告とみなすのが妥当です。この矛盾を機械的に検出する仕組みは未実装です。

この9件から、スキルの品質についての結論は出せません。確認された不具合も、改善の証拠もありません。

### 限界

- ラベルは構成によるもので、人の確認前です。人手確認済みラベルでの見逃し率・誤警告率は不明です。
- 生成、既存のLLM採点、Ragas の評価器のすべてが同じモデル系列（Claude）です。誤りの傾向が相関し、独立した確認になっていません。
- 実生成は3抜粋・独立した出典2文書です。反復3回は独立の標本ではありません。
- Ragas 既定の英語プロンプトと日本語プロンプトの比較は未実施です。繰り返し実行による分散と `coverage=low` との比較は、2026-10-17 に人工例で実施しました（下記）。
- 判定規則の一部はスモーク3件を見た後で固めました。

### 追加の検証（2026-10-17）

2026-10-16 の「次に必要なこと」のうち、人手のラベル付けを除く項目を、人工例で実施しました。設定は同じ（`atomicity=high`、`--profile gov-org`、評価器は Claude CLI）で、macOS、Python 3.13.16 で実行しました。調整用側の出典だけを使い、最終評価用は使っていません。ラベルは**構成によるもので人の確認前**です。記録は [`evals/ragas-calibration/results-2026-10-17/`](../evals/ragas-calibration/results-2026-10-17/README.md) にあります（新規の実行は定価換算で合計約7.5 USD）。

**追加した人工ケース（21件）。** 「原則として」の追加、「絞らなければならない」→「絞る」、「可能性があります」→「かかります」、「すべての削除」→「通常の削除」、必要なフラグの脱落、「限って…べき」→「とよい」、「からのみ」→「の権限で」、探索順序の脱落、限定の脱落、「場合がある」の削除、対比の反転、相談先の入れ替え、推奨→指示の15件（期待は fail）と、正当な言い換え4件・無変更2件（期待は pass）です。出典は、デジタル庁・Python・Kubernetes・青空文庫（寺田寅彦・牧野富太郎）・IPA の**調整用側**の抜粋です。ケースとラベルは `evals/ragas-calibration/artificial-cases-subtle.json`、`artificial-labels-subtle.json` にあります。以下の比較は、既存の13件と合わせた34件（欠陥あり23、なし11）です。

**1. 微妙な欠陥21件（既定の設定、1回）**

| 指標 | 欠陥あり（15件） | 欠陥なし（6件） |
|---|---|---|
| factual の信号 | 7/15 | 0/5（1件は採点不能） |
| rubric の信号 | 15/15 | 0/6 |
| 違反した観点が fail | 15/15 | — |

- **factual は微妙な欠陥を半数近く見逃しました。** precision と recall がともに 1.0 だったのは 8/15 で、「原則として」の追加、必要性の脱落（「絞らなければならない」→「絞る」）、「限って…べき」→「とよい」、推奨→指示などです。主張抽出が、修飾や強さの変化を別の主張として扱わないためと推測しますが、確認はしていません。
- rubric は 15/15 で信号を出し、違反した観点も fail にしました。ただし**欠陥あり1件あたり fail になった観点数は 1〜6**（中央値3）で、観点の弁別は不十分です。
- 欠陥なし6件に、rubric の誤警告はありませんでした。

**2. 繰り返し実行のばらつき（人工13件×3回）**

| 指標 | 結果 |
|---|---|
| rubric の信号（保持の観点のいずれかが fail）が回ごとに変わったケース | 0/13 |
| factual の信号が回ごとに変わったケース | 2/13（`strength-s3b`: True,True,False。`paraphrase-s6`: True,False,False） |
| fail になった観点の**集合**が回ごとに変わったケース | 7/13 |
| 観点の値（pass／fail／uncertain）が回ごとに変わった数 | 7/91（7.7%） |
| precision の最大の幅、recall の最大の幅 | 0.34、0.25 |
| 欠陥あり8件で信号が出た数（回ごと） | factual 8,8,7、rubric 8,8,8 |
| 欠陥なし5件で信号が出た数（回ごと） | factual 1,0,0、rubric 0,0,0 |

- rubric の「何か壊れている」という信号は、この13件では回ごとに変わりませんでした。一方、**どの観点が fail になるかは回ごとに変わります**（7/13件）。観点別の判定は、1回の値を使わず、多数決や人の確認と組み合わせる必要があります。
- factual の値と信号は回ごとに変わります（幅 0.25〜0.34）。1回の値の差は、ばらつきの範囲内の可能性があります。
- 繰り返しは、同じ設定の独立な呼出しですが、温度と乱数種は CLI から指定できません（不明）。3回は独立な標本とは言えず、率は記述値です。

**3. `coverage=low` との比較（factual のみ、34件、各1回）**

| | 欠陥あり（23件）で信号 | 欠陥なし（11件）で信号 |
|---|---|---|
| `coverage=high`（既定） | 15/23 | 0/10（1件は採点不能） |
| `coverage=low`（Ragas の既定） | 19/23 | 0/11 |

- 「`coverage=high` が本用途に適する」という仮説は、**この34件では支持されませんでした**。`high` が見逃して `low` が拾ったのは4件（`order-py`、`necessity-s5`、`strength-py`、`strength-up-org`）、その逆は0件です。誤警告はどちらも0件でした。
- 一方、`low` も 4件（`hedge-s3a`、`timing-s6`、`hedge-k8s`、`hedge-essay`）を見逃しました。**どちらの設定でも factual 単独では微妙な欠陥を取りこぼします。**
- 差の4件は、上のばらつき（factual の信号が回ごとに変わる）の範囲内の可能性があります。既定を `low` に変える根拠にも、まだなりません。

**4. 観点の弁別の指示（`--discriminate`、rubric のみ、34件、各1回）**

| | 既定 | `--discriminate` |
|---|---|---|
| 欠陥あり23件で fail になった観点数（平均／中央値） | 3.65／3 | 2.17／2 |
| fail が1観点だけだった件数 | 1 | 7 |
| rubric の信号（欠陥あり） | 23/23 | 23/23 |
| rubric の信号（欠陥なし11件） | 0/11 | 0/11 |
| 違反した観点が fail | 23/23 | 22/23 |

- 指示で、**他の観点への「もらい fail」は減りましたが、なくなってはいません**（23件中16件が2観点以上で fail）。信号の検出と誤警告は変わりませんでした。
- 狙った観点を外した1件は `hedge-k8s`（「デフォルトの状態はSuccessです」→「通常はSuccessとして扱われます」）です。`modality_strength` は pass、`condition_scope` が fail でした。この欠陥は、強さの変更とも範囲の変更とも読めるため、構成上の分類（`modality_strength`）が曖昧でした。
- 複数回の多数決は、呼出しを増やすため、この実験では実装していません。上の繰り返し実行のデータでは、3回で信号が割れたのは factual の2件だけで、rubric の信号は割れませんでした。

**5. 値と理由の矛盾の検出（語の有無による試行）**

2026-10-16 に見つかった矛盾は `g001`（値は fail、理由は「条件・範囲の脱落や変更はない」）でした。これを機械的に拾う方法として、理由の語の有無で拾う方式を2通り試しました。

- 理由の全文で「異なる」「脱落」などを探すと、91〜147件の観点別採点のうち15〜19件が候補になりましたが、多くは正当な判定でした。fail の理由が「他の部分は保たれているが、…のため fail」と書き、pass の理由が「他の観点の変化に触れたうえで、この観点の対象外」と書くためです（観点の弁別としては正しい書き方です）。
- 結論の文（最後の文）だけを見ると、721件の観点別採点（再実行の重複を含む）で16件が候補になりました。うち**矛盾は `g001` の1件だけ**で、他の15件は「後半は保たれている」などの部分的な記述でした。

語の有無では、既知の1件以外の矛盾を見つけられず、誤検出が多いため、**ツールには入れませんでした**。判定と理由を構造化して別々に出させる、別の呼出しで整合を確認する、といった方法は未実施です。この1件が偽警告に当たる rubric 出力の信頼性の問題は、解決していません。

### 追加の検証の限界

- ラベルは構成によるもので、人の確認前です。欠陥は私が構成し、rubric の観点も私が設計しています。欠陥の分類は設計者の見方に偏ります（`hedge-k8s` の例）。

- 比較（`coverage`、`--discriminate`）は各1回です。繰り返しのばらつきを測ったのは、既定の設定の13件だけです。
- 生成、LLM採点、Ragas の評価器は同じモデル系列（Claude）です。誤りが相関し、独立した確認になっていません。
- 全ケースを同じ7観点（`gov-org`）で採点しました。エッセイ向けの観点（`rhetoric_tone`、`sentence_function`）と、文書群ごとの観点の組は検証していません。
