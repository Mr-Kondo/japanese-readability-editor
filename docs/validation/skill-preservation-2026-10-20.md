# Skill 軽量化の前後の、意味保存の比較(2026-10-20)

[Issue 86](https://github.com/Mr-Kondo/japanese-readability-editor/issues/86)。[トークンの計測](skill-token-usage-2026-10-19.md)で測っていなかった、B(Rewrite)の出力の意味保存を、v0.15.2(前)と v0.16.0(後)で比べた記録です。

## 結論

- 意味保存は、前も後も、同じ水準でした。48件のうち、**前は 44 pass / 4 fail、後は 45 pass / 3 fail** です。差は1件で、偶然の範囲です。軽量化による劣化は、この計測では見えませんでした。
- 採点の対照12件(正解が分かっている)は、前後とも**12/12 正解**でした。
- どちらの版にも、**同じ種類の fail が残っています**。軽量化とは別の、既存の課題です([Issue 90](https://github.com/Mr-Kondo/japanese-readability-editor/issues/90))。

## 方法

- 評価ツール: `tools/evaluate_readability.py --skill-dir <Skill のフォルダ> --execute`。`--skill-dir` を足して、Skill を隔離した一時プロジェクトに入れ、ツールを使える状態で `claude -p` を流す方式にした(従来は、SKILL.md などをプロンプトに貼り、ツールなしで生成していた)。採点は従来どおり、Skill なし・ツールなしの隔離で、盲検(版名を与えない)。
- ケース: `evals/readability-generalization-cases.json`(16ケース)× 3回 = 48件の出力。ケースは、日常の案内、規程、手順、報告、数式、コード・URL を含む。15件がモード B、1件(x16)がモード A。
- 採点: 同じモデル(Sonnet 5.5)・同じ指示で、15件ずつ。pass / fail / uncertain と理由。対照12件(わざと意味を変えた候補)を混ぜて、採点が見逃さないかを確かめた。
- 版: 前 = v0.15.2(`git archive 73aec7a skills`)、後 = v0.16.0(`git archive v0.16.0 skills`)。2つを同時に実行した。Claude Code 2.1.292、モデルは両方 `claude-sonnet-5-5`。
- 記録: [evals/skill-dir-preservation/](../../evals/skill-dir-preservation/)(出力、採点、理由)。

## 結果

| 版 | pass | fail | uncertain | 対照12件 |
|---|---|---|---|---|
| v0.15.2(前) | 44 | 4 | 0 | 12/12 正解 |
| v0.16.0(後) | 45 | 3 | 0 | 12/12 正解 |

fail の中身(回数はケースごとの3回中):

| ケース | 前 | 後 | 内容 |
|---|---|---|---|
| x08 | 1 | 1 | 常体の原文を、敬体にした(「処理対象にする」→「処理対象にします」)。後は、「承認済みで検証済みの」と書き換えて、誰が承認したかも曖昧になった。 |
| x14 | 1 | 1 | 原文末尾の「この報告に、実際には行っていない再発防止策を…追加しない」という、報告の方針を示す文を落とした。 |
| x15 | 2 | 0 | 方針の表明「広げないようにします」を、読み手への依頼・禁止(「広げないでください」「広げてはいけません」)にした。 |
| x16 | 0 | 1 | モード A。資料の「保守チームが通知設定を改めた」の主体を落とした。 |

## 読み方

- 前後の差(4件と3件)は、1件です。3回ずつでは、ケースごとの差も読めません。x15 の 2→0 と x16 の 0→1 は、偶然の揺れの範囲です。
- 採点はモデルが行うので、採点の誤りが混ざりえます。ただし、fail の理由は、すべて原文と出力の具体的な違い(文体、文の脱落、働きの変化、主体の脱落)を挙げていて、読んで妥当でした。対照12件も全問正解でした。
- この比較は、**トークン計測の「最終版」とは別の版**(v0.16.0)を測っています。最終版(v0.17.0)は、`skill_info.py` と `VERSION` を足しただけで、本文の増減は1文です。
