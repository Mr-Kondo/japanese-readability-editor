# 文章を定量・定性で評価する

`tools/review_readability.py` は、自動検証と人間による手動検証を扱う開発用ツールです。スキルの配布物には含めず、Python標準ライブラリだけで動きます。入力文章を生成・推敲するツールではありません。

旧新版・スキル有無の二候補を比べる場合は、後述の[匿名二候補比較](#匿名二候補比較モードb)を使います。`tools/compare_readability.py` も追加依存なしで動きます。

| 方法 | 定量評価 | 定性評価 | 実行環境 |
|---|---|---|---|
| 自動・表層検査 | 原文／候補の文字数、文数、段落数、平均文長、漢字率、長文・長段落件数 | 数値・URL・コード・用語・否定・条件等の差と照合理由、読み直す箇所 | Python、通信不要 |
| 自動・LLM採点（任意） | 理解しやすさ・自然さ・文体適合の1〜5評点、保持判定・選好の分布 | 引用を含む判断理由、修正案 | 既存認証のClaude CLI。外部送信あり |
| 手動 | 同じ1〜5評点、保持判定、原文との選好。集計は分布・平均・欠測 | 根拠箇所の引用、読者への影響、任意修正案 | ローカルHTMLを開けるブラウザ |

文字数や指摘件数を品質点へ換算しません。表層検査の意味保持は原則 `uncertain`（未判定）です。CだけはJSON内の原文字列を保ってLFを追加したか決定的に検査します。Bの表層比較は既存の `compare_rewrite.py` をregexで使い、意味変更の候補を示します。国語表記の検査や出典の事実確認はこのツールの対象外です。

## 入力を用意する

リポジトリのルートで実行します。別の場所から使う場合は、スクリプトと入力に絶対パスを指定してください。例題は人工的な失敗例と改行例で、品質改善の実測ではありません。

```bash
python3 tools/review_readability.py prepare --input evals/human-review-example.json --out-dir /tmp/jre-manual
```

`/tmp/jre-manual/review.html` を通常のブラウザで開きます。HTTPサーバーやライブラリのインストールは不要です。Windowsでは書込可能な新規フォルダを `--out-dir` に指定してください。

独自データは次の形式にします。

```json
{
  "schema_version": 1,
  "cases": [{
    "id": "doc-1",
    "document_id": "source-1",
    "mode": "B",
    "request": "条件と数値を保って推敲してください。",
    "audience": "利用申請をする社員",
    "context": "判断に必要な資料・用語・保持事項を記入する。",
    "original": "管理者の承認後、30分以内に実行できます。",
    "candidate": "管理者が承認した後、30分以内に実行できます。",
    "provenance": {"model": "生成時のモデル識別子", "skill_version": "生成時のスキル版"}
  }]
}
```

`id` は候補ごとに一意、`document_id` は同じ原稿の反復に共通の値を指定します。省略時は `id` を使います。生成条件・スキル版は任意の `provenance` に記録してください。Aは指示・資料への適合、Bは意味保持、Cは改行挿入、Dは小説の操作契約を評価します。Dには `operation` として `plan/draft/continue/revise/critique` が必要です。B/CとDのcontinue/revise/critiqueには原文が必要です。A/Dは原文との選好を付けず、単独評価します。

既存の `tools/evaluate_readability.py` の `run.json` も直接指定できます。各ケースの依頼に明示された「モード A/B」を読み、候補48件と原稿16件などを区別して保持します。モードを特定できない記録は、推測せず拒否します。他形式は上記の `cases` に変換してください。既存のモデル採点結果は手動画面へ取り込みません。

## 手動で評点とフィードバックを残す

1. 評価者IDを入力する（仮名可）。
2. 原文・資料・依頼と候補を照合し、保持／操作契約を `pass/fail/uncertain` で評価する。
3. 理解しやすさ・自然さ・文体適合を各1〜5で評価する。根拠不足なら未評価のまま残す。
4. B/Cでは原文と比べた選好を選ぶ。保持が不合格・判断不能なら選好も「判断不能」にする。
5. 根拠・理由へ引用と読者への影響を記入する。問題がなければ、保たれた関係や判断根拠を書く。修正案は任意。
6. 「回答JSONを保存」を押す。ダウンロード先への保存を確認する。「以前の回答JSONから再開」で続きから評価できる。

評点は `1=大きな問題、2=問題あり、3=許容、4=良い、5=非常に良い` です。未入力文書は飛ばせます。入力を始めた文書には保持判定・選好・理由が必要で、入力途中の文書があると保存を拒否します。未評価の評点は `null` で保存します。自動保存はありません。未保存で閉じようとすると警告します。保存済み回答を読み込む際も、未保存入力があれば置換前に確認します。

この単独評価画面では、原文と候補の役割を明示しています。旧新版を伏せる場合は匿名二候補比較を使います。フォームの「理解しやすさ」は印象に基づく評点で、理解率の実測ではありません。

## 自動で検証する

通信を使わない表層検査:

```bash
python3 tools/review_readability.py auto --input evals/human-review-example.json --out-dir /tmp/jre-auto
```

`automatic.json` と `automatic.md` に原文・候補の計測、検出箇所と理由、検査範囲を保存します。指摘なしでも意味保持の合格にはしません。

LLMによる定量評点と定性講評も取得する場合:

```bash
python3 tools/review_readability.py auto --input evals/human-review-example.json --out-dir /tmp/jre-llm --judge
```

**`--judge` は依頼・原文・資料・候補・対象読者をClaudeへ送信します。** モデル呼出しは既存の `evaluate_readability.py` のClaude CLI設定（sonnet / medium）を再利用します。必要なCLIと認証は利用者が用意し、利用枠を消費します。モデル識別子・生応答・プロンプトのハッシュを保存し、LLMの評点と講評は `llm-answers.json`、集計は `summary.json` / `summary.md` に保存します。通信不要の経路でLLM採点が動いたとは報告しません。

途中でCLIが失敗したり不正なJSONを返したりした場合は、`automatic.json` を `failed` にし、成功済みの回答と生応答を残します。完全な集計は作りません。Cの原文字列検査の不合格をLLMの合格で上書きしません。再実行には別の出力先を使ってください。

終了コードは `0=検査完了（品質合格とは限らない）、1=決定的検査またはLLMで不合格あり、2=入力・保存・実行エラー` です。自動結果の `uncertain` は未判定として残ります。

## 回答を集計する

保存した回答JSONのパスを指定します。複数人の回答を並べて指定できます。

```bash
python3 tools/review_readability.py summarize --input /tmp/jre-manual/tasks.json --answers /path/to/human-answers.json --out-dir /tmp/jre-summary
```

出力は `summary.json` と `summary.md`。人間／LLM、モード別に、以下を示します。

- 文書数、候補数、評価者数、予定回答数、回答済み・欠測。
- 保持判定の分布、全予定回答を母数とする不合格率。欠測数も必ず併読する。
- 合格回答に限定した選好分布。不合格を除いた選好を全体の改善率とは扱わない。
- 各評点の件数・分布・記述的平均・未評価数。評点の未評価数は回答済み内で数え、未回答文書は `missing_reviews` に数える。
- 評価者別の根拠・理由・修正案。

対象と評価基準のハッシュが異なる回答、未知・重複ID、不正な評点、同一方法・同一評価者の二つの保存ファイルは拒否します。改訂回答は最新ファイル一つだけを渡してください。エラー時は `review failed: ...` と表示し、集計前の入力不正なら出力先を作りません。出力先が既存の場合も上書きを拒否します。

評価者が全候補を担当する前提です。一部だけ割り当てた評価者も、残りは欠測として数えます。LLM実行の識別は回答ファイル単位で、異なる生成・採点モデルを横断した因果効果をこの集計から主張しないでください。

## 匿名二候補比較（モードB）

設計調査の初版範囲に合わせ、原文を共有する二候補を評価します。準備用JSONは `evals/blind-comparison-example.json` の形式です。`mode` は `B` を明示し、単独評価の `candidate` の代わりに `candidates` へ版名と本文の組を二つ指定します。全ケースで同じ二つの版名を使います。`tie` と `uncertain` は集計用の予約語で、版名には使えません。

```json
{
  "schema_version": 1,
  "cases": [{
    "id": "doc-1",
    "document_id": "source-1",
    "mode": "B",
    "request": "条件と数値を保って推敲してください。",
    "audience": "利用申請をする社員",
    "original": "承認後、30分以内に実行できます。",
    "candidates": {
      "baseline": "承認後、30分以内に実行できます。",
      "revision": "承認された後、30分以内に実行できます。"
    }
  }]
}
```

評価者の仮名IDを指定して配布物を作ります。全評価者へ全件を割り当てます。

練習例の主催者向け確認点は次のとおりです。回答を代入する採点用の正解データではありません。独立評価後の基準合わせに使います。

| 例 | 確認点 |
|---|---|
| 数量・条件 | `revision` は30分を3分に変え、管理者承認の条件を削除。意味保持の不合格を自然さで相殺しない |
| 接続設定 | 文を分けても保存→確認→接続不可なら連絡という順序・条件を保っているか。読みやすさの選好は評価者が判断する |
| 文の働き | `revision` は方針表明を相手への依頼に変更。主体・発話目的の違いを記録する |

```bash
python3 tools/compare_readability.py prepare --input evals/blind-comparison-example.json --reviewers reader-a reader-b --out-dir /tmp/jre-pairs
```

出力は次のとおりです。

- `organizer.json`：主催者用。版名との対応表、割付日時、入力のハッシュ、配布データを保持します。評価者には渡しません。
- `reader-001/`、`reader-002/`：指定順の評価者別配布物。`review.html` と `tasks.json` だけを対応する評価者へ渡します。HTMLだけでも評価できます。

配布データから版名・生成情報・元の文書IDを除き、左右候補と匿名IDに置き換えます。左右は評価者ごとにランダムに決め、独立文書数で左右差を最大1件に抑えます。同じ `document_id` の反復は同じ向きです。再生成すると割付が変わり得るため、同じ調査は保存した配布物から再開してください。`organizer.json` も再集計のため保管します。

本文、依頼、文脈、評価者の仮名はそのまま配布されます。そこに版名を記入しないでください。文体や原文との一致から版を推測できる可能性は残り、匿名化だけで完全な盲検を保証しません。モデル採点結果や表層警告は画面に出しません。

画面では各候補に保持判定、三軸の評点、判定理由、任意の修正案を記録します。「問題箇所を追加」で、候補内の引用・種類・重大度・理由を複数記録できます。欠落の指摘は周辺の文を引用して説明します。引用が候補内に完全一致しない回答は保存・集計を拒否します。

両候補の保持判定が合格になったときだけ「左／右／同等／判断不能」の選好を選べます。片方でも不合格・判断不能に戻すと選好も判断不能へ戻ります。全体の比較理由は必須です。原文の方がよければ、その旨も比較理由に残してください。未入力文書は飛ばせますが、入力を始めた文書は左右の保持判定・理由と比較理由を完成させて保存します。評点は未評価のままでも保存できます。回答JSONの明示保存・再読込に対応し、自動保存はしません。

集計には主催者ファイルとダウンロードした回答の実際のパスを指定します。

```bash
python3 tools/compare_readability.py summarize --organizer /tmp/jre-pairs/organizer.json --answers /path/to/reader-a-answers.json /path/to/reader-b-answers.json --out-dir /tmp/jre-pair-summary
```

`summary.json` と `summary.md` に、割付数・回答数・欠測数、候補別の保持判定と全割付を母数にする不合格率、評点分布・平均、両候補合格内の選好を保存します。`summary.json` の `qualitative` には候補別の引用・理由・修正案を保持します。評点の欠測は回答済み内の `scores.*.missing`、未回答文書は `missing_reviews` で分けます。ファイル未提出者も割付数・欠測数に含み、反復出力を独立文書と数えません。

回答の評価者・配布ハッシュ・基準版の不一致、重複回答・不正な評点を拒否します。一人につき最新の回答ファイル一つを渡してください。入力不正では出力先を作らず、既存の出力先も上書きしません。終了コードは `0=処理完了、2=入力・保存エラー`。不合格を含む正常な集計でも0です。異常時は `comparison failed: ...` を表示します。

同じ二候補JSONから自動検証も実行できます。

```bash
python3 tools/compare_readability.py auto --input evals/blind-comparison-example.json --out-dir /tmp/jre-pair-auto
```

既存の自動検証を再利用し、各候補を独立に検査します。`tasks.json` の `provenance.variant` で版名、`document_id` で原文を追跡できます。`--judge` を付けると各候補をClaudeへ送信し、単独評価の評点・原文との選好・理由を取得します。版名と生成情報はモデルへ渡しません。人手の二候補間選好とは別の評価で、自動集計から二候補の勝率を出しません。自動検証の終了コードは単独評価と同じ `0/1/2` です。

人手回答とLLM回答は混ぜず、匿名比較の集計は人手専用です。理解問題・裁定画面・信頼区間・スキルへの自動反映は含めません。

## 限界と改善への接続

平均評点を単一の総合品質点にしません。評点が高くても意味改変は独立した不具合です。反復生成や複数人の票を独立文書と数えず、信頼区間・一致係数・有意差は未実装です。Cの検査対象もJSON内の文字列であり、元ファイルの文字コード・バイト保持までは保証しません。

指摘を人が確認し、繰り返す失敗を回帰ケースに変え、ルール・例を必要な範囲だけ修正します。その後、同条件で旧新版を未使用文書に適用して確認します。このツールはスキルを自動更新せず、理解度・読解時間・改善率を予測しません。

手法の根拠は[人手評価の実践指針](https://aclanthology.org/W19-8643.pdf)、[日本語文書単位の平易化評価](https://aclanthology.org/2026.lrec-1.85/)、[意味保持と理解の評価](https://aclanthology.org/2024.tacl-1.24.pdf)を参照してください。
