P1 の補助群です。P0 群の整備を優先し、PDF の大量変換や独自の抽出器は作りません。今回は、既存の形式（Markdown）から正確に取り出せる資料だけを収集しました。

## 目的

行政・翻訳技術文書だけに偏らず、組織の役割・ポリシー・導入説明（役割、担当、推奨と義務、導入順序、条件、専門用語）を保てるかを調べます。読みやすさと、ポリシー内容の法的な正しさは分けます。後者は評価しません。

## 取得で分かったこと

- Markdown は `tools/extract_markdown_text.py` で、空行で区切ったブロックの順に取り出します。記法（`**太字**`、箇条書きの字下げ、`【 】`）は残します。**IPA の資料は Markdown のまま編集される文書なので、記法を保つことも保持対象です。**
- 運用ガイドの多くは、`[会社名]` のようなプレースホルダーを含む**記入用テンプレート**です。空欄を事実として埋めず、プレースホルダーを含むブロックは採りません（`x-ipa-ospo-template`）。
- 規程の雛形の「条文サンプル」は、`【 】` で囲んだ選択項目が多く、確定した文言として読めません。条文は第5条だけを候補にし、第6・7・11条は解説とカスタマイズだけを候補にしました。
- 同じ文面のチェックリストの注意書きが4ファイルにあります。1か所（`ipo-checklist`）だけを候補にしました。
- 原文に誤字があります（例: 第7条の解説の「標準化させるようにしきます」）。直さず、保持要件に記録しました。

## 抜粋の選び方と分割

選定基準は台帳の `groups.ipa-oss.selection` に記録しています。選び方は、Markdown をブロックに分け、「しなければならない」「してください」「推奨」「必要があります」「場合」等を含み、プレースホルダーを含まないブロックを走査して、トピックが重ならないよう選ぶ方法でした。走査した全ブロックは記録していません。**手作業の選定であり、無作為抽出ではありません。**

| 側 | 系列 | 抜粋 | 主な内容 |
|---|---|---|---|
| 調整用 | 運用ガイド | 9件 | OSPO はサポート窓口ではない、バーチャルチーム型、評価の三段階、ライセンスの3区分、相談のタイミング |
| 最終評価用 | 規程の雛形 | 9件 | 第5条の評価・SBOM・遵守、事前承認の理由、二段階方式、公開前の確認、脆弱性対応の体制 |

分割は系列単位で、モデル出力の生成・閲覧の前に決め、台帳に日付付きで記録しました。限界は次のとおりです。

- **同じ1つのキット**の2系列で、著者・版の独立性は低いです。2系列は主題が近く（OSPO と OSS の管理）、独立した原本とは言えません。
- OSPO の役割を扱う第4条は、運用ガイドの「OSPOとは」と主題が重なるため、採りませんでした（`x-ipa-p04`）。
- 変更不要の対照例は `ipo-checklist` です（評価前に私が判断したもので、人の確認が必要）。
- キットは未完成で、今後大きく変わる可能性があります。集計の信頼区間は意味を持たず、記述的な予備評価にとどまります。
- IPA の資料は、資料ごとに利用条件の表示が異なります。ワークブックは CC BY 4.0 などの別の表示を持つため、この台帳の CC0 を当てはめません。ワークブックと他の PDF は、PDF の変換が必要なため、この段階では収集していません。

## 利用条件の確認

読んだ内容（2026-10-17）:

- リポジトリの `LICENSE` は CC0 1.0 Universal です。README は「本キットに含まれるテキストおよびドキュメントは CC0 1.0 の下で提供」「クレジット表記不要」と述べます。
- README は、ポリシーやライセンス解説が一般的な雛形であり、運用には自社の法務・知財部門の確認が必要だと述べます。この文書の**内容の法的な正しさは評価の対象外**です。

台帳の `license.body` に、出典と加工（抜粋、内容の変更なし）の表記を書きました。CC0 のため表示は法的には不要ですが、出所として記しています。**第三者の著作物の有無は、人が確認して `third_party_content` を `none` にするまで採用しません。**

## 保持要件

`kind` の対応は、[Python の文書群](public-documents-python.md#保持要件)と[青空文庫](public-documents-aozora.md#保持要件)の表に加えて、次のとおりです。

| 保持するもの | `kind` | 補足 |
|---|---|---|
| 役割・担当・主体 | `actor` | 「従業員が従い、管掌部門が支援する」のように、主体を入れ替えない |
| 推奨・義務の強さ | `strength` | 「してください」「推奨します」「するものとする」「ならない」を弱めない |
| 条件・導入順序 | `condition`、`claim` | 初期段階→発展段階→成熟段階、「作業を進める前に」 |
| 専門用語・区分名 | `term` | OSPO、SBOM、SCA、CVD、CVSS、区分名（GPL、AGPL、LGPL、MPL） |
| Markdown の記法 | `notation` | `**太字**`、箇条書きの字下げ、`SECURITY.md` などのファイル名 |

特に取り違えやすい箇所を保持要件にしました。例: 「OSPO は判断を代行する組織ではなく、支援する組織」、セキュリティリスクの相談先が OSPO ではなくセキュリティ部門であること、チェックリストは全項目を満たす必要がないこと、「事前に」評価すること。

## 評価の設定

- モードBを明示し、対象読者（例: 開発者、OSPO 担当者、経営層）は生成前に決めて `audience` に書く。`request` も固定する。**対象読者・依頼は未決定。**
- 比較・統計用の `document_id` は台帳の `source_id`、理解問題用は抜粋IDにする（[接続の制約](public-document-evaluation.md#既存ツールとの接続)）。
- 組織運営文書の群として独立に集計する。他の文書群と合算しない。
- 読みやすさと、ポリシー内容の正しさを分ける。後者（法務の妥当性）は評価しない。
- テンプレートの空欄を、事実として埋めない。

## 人が行うこと

1. 各 `candidate` について、台帳の本文を原本のファイル（固定したコミット）と見比べ、`correspondence` に確認者・確認日を記入する。
2. 第三者の著作物の有無を確認し、`third_party_content` を確定する。
3. `preserve` の各項目と `questions` を原文と照合し、`confirmed_by`・`reason`、`verified_by`・`verification_reason` を記入する。修正や削除をしてよい。
4. `ipo-checklist` を変更不要の対照例にしてよいか判断し、`no_change_reason` を確定する。
5. 採用するものの `status` を `adopted` に変える。`--readiness` の出力が空になるまで繰り返す。
6. 対象読者・依頼を決め、`cases` JSON を作って[計画の手順](public-document-evaluation.md#手順)に進む。
7. ワークブックなどの PDF を使う場合は、資料ごとの利用条件の表示を取得時に確認し、台帳へ追加する。
