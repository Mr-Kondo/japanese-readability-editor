## v0.18.0

書き換え(モード B)の既定の手順を変えた。スクリプトを実行できる環境では、返す前に `compare_rewrite.py` で元の文と照合する。

### 変更点

- `SKILL.md`: B で、書き換える前の文章を保存し、書き換えた後に `compare_rewrite.py` で照合して、挙がった箇所を元の文と見比べてから返す、と必ず行う手順にした。短い文章でも省かない。照合が終わったら、保存先を削除する。「書き換えた後の照合」の冒頭にも、同じことを書いた。
- 判断の経緯: Issue 90。短い文章で残る意味保存の失敗(常体→敬体、方針を示す文の脱落)は、モデルが自分で照合を済ませたつもりで、スクリプトを実行しなかった回に多かった。実行を必ずにすると、2ケース合計で 8/20 から 1/20 に減った(道具なしの試験)。

### 測ったこと(Sonnet 5.5。詳細は [docs/validation/skill-preservation-2026-10-20.md](https://github.com/Mr-Kondo/japanese-readability-editor/blob/main/docs/validation/skill-preservation-2026-10-20.md))

- ファイルを直す依頼での `compare_rewrite.py` の実行: 21%(5/24)から **100%(24/24)**。入力側のトークンは **+29%**(短 +21%、中 +32%、長 +33%。API 呼び出しが1回増える)、費用は +6〜10%(増えた入力の大半がキャッシュの読み取り)。トークンの削減(v0.16.0)の方針とは、意味の保存を取る形で逆になる。
- 意味保存(全16ケース×3回): 旧版 pass 42 / fail 3、この版 pass 42 / fail 4。悪化は見えなかった。

### 訂正(2026-10-21)と未確認

- 最初の版のこのノートは、「意味保存の試験は道具なしで流した」と書いていた。**誤り**で、`--skill-dir` の生成は道具ありだった(記録の `flags` 欄が従来の値のままで、誤解した)。
- ただし、この版の意味保存の試験は、スクリプトを実行したかを記録していなかった。流し直したところ、**本文だけを返す依頼では、実行は 10/40(25%)しかなかった**(ファイルを直す依頼では 24/24)。v0.18.1 で直した。
- 未確認: Opus 5.5、他のエージェント、数万字の文書。スクリプトを実行できない環境(Claude.ai のチャットなど)では、従来どおり、1文ずつ突き合わせるだけ。
