推敲で、作業主体、実施条件、完了条件、必須／推奨の強さを変えないかを調べます。

## 取得で分かったこと

- DS-110 は DS-100 の条文を逐条で引用します（引用部分は `OriginalBodyText` スタイル）。本文が重なるため、DS-100 と同じ系列（`da-ds-100-110`）として扱い、引用行は抜粋しません。
- 標準テンプレートの ZIP には Word だけが入り、PDF はありません。そのため、PDFとの照合ができません。
- テンプレートには「XXX」「○○省」の未記入欄と、【〜の場合】の条件付き選択ブロックが多くあります。未記入欄を含まず、確定した文言として読める段落だけを選びました。選択ブロックは採用しません。
- Word の自動番号（(1)、ア等）は復元していません。「前項」「上記（1）」のような参照は、参照先が抜粋内にあるものだけを選びました。

## 抜粋の選び方と分割

選定基準は台帳の `groups.digital-agency.selection` に記録しています。

- その抜粋だけで、手順・役割・要件のいずれかが読める。主体・条件・期限・例外・成果物のいずれかを含む。
- 表・図・他節の番号参照に依存して文意が欠けない。依存するものは除外し、理由を記録する。
- テンプレートの未記入欄や条件付き選択ブロックを含まない。DS-110 は引用ではなく解説部分だけ。
- 変更不要の対照例を含める（`dapt-acceptance`。評価前に私が判断したもので、人の確認が必要）。

選び方は、各文書の本文を段落単位で抽出し、「場合」「までに」「以内」「ただし」「してはならない」等を含む段落を走査し、トピックが重ならないように選ぶ方法でした。走査した全段落は記録していません。**手作業の選定であり、無作為抽出ではありません。**

| 側 | 出典 | 抜粋 | 主な内容 |
|---|---|---|---|
| 調整用 | DS-120（第5章）、要件定義書テンプレート | 3件 | 要件定義・運用要件の記述 |
| 最終評価用 | DS-100、DS-110（第6章）、調達仕様書テンプレート | 8件 | 予算・計画・調達・契約 |

分割はモデル出力の生成・閲覧の前に決め、台帳に日付付きで記録しました。同じ条項の解説やテンプレートが両側に入らないよう、トピックでも分けています。限界は次のとおりです。

- トピックと分割が交絡します。調整用で見えた失敗が要件定義に偏り、最終評価用は調達・契約に偏ります。
- 全て同じ提供者（デジタル庁）の標準ガイドライン群で、著者・系列の偏りは抑えられていません。
- 独立した原本は、調整用2、最終評価用2（DS-100 と DS-110 は同系列のため1と数える）です。集計の信頼区間は意味を持たず、記述的な予備評価にとどまります。

## 利用条件の確認

読んだ内容（2026-10-16）:

- コピーライトポリシー（最終更新 2026-05-12）は、権利表記がない限りコンテンツに PDL1.0 を適用すると述べます。
- PDL1.0 は、出典の記載と、編集・加工した旨とその主体の記載を求めます。加工した情報を、国や府省が作成した未加工の文書であるかのように公表することを禁じます。第三者が権利を持つ部分は、利用者の責任で確認します。
- 5つの Word の本文・ヘッダ・フッタに個別の権利表記は見つかりませんでした（文字列検索のみ。PDF の表紙や奥付は確認していません）。

台帳の `license.body` に、出典の表記と加工の表記を書きました。加工主体は `japanese-readability-editor` としています。**この表記と、第三者権利の有無は、人が確認して `third_party_content` を `none` にするまで採用しません。** 予備確認では、法令・申合せ・通達の名称を参照するだけで、図や第三者の著作物の転載は見当たりませんでした。

## 保持要件

`preserve` の `kind` に、次の対応で記録します。いずれも抜粋内の引用（`quote`）と、人の確認者・理由が必要です。

| 保持するもの | `kind` | 補足 |
|---|---|---|
| 順守内容（Normative）／参考内容（Informative） | `strength` | 項目の `strength` に `normative` または `informative` を書く。判断の根拠文を `quote` にする |
| 誰が行うか | `actor` | 主体の追加・欠落・入れ替えを不具合として扱う |
| 期限・時期 | `deadline` | |
| 前提・実施条件 | `condition` | |
| 例外 | `exception` | |
| 成果物・完了条件 | `deliverable` | |
| 主張・数値 | `claim`、`number` | |

`allowed_changes` には、許容する変更を書きます。草案では全項目に「文の分割・結合、語順や接続表現の整理（主体・条件・期限・義務の強さ・完了条件を変えない範囲）」としました。専門用語の和語化と、参考情報を義務に変える変更は、許容に入れず不具合として評価します。

特に取り違えやすい箇所を保持要件にしました。例: 禁止（してはならない）の弱体化、「いずれか」と「かつ」の論理、再委託の「承認」と再々委託の「報告」、「求めない」と「提案すること」、「必ずしも全てを〜わけではない」の部分否定、「やむを得ない」を推奨と読み替えること。

## 評価の設定

- モードBを明示し、対象読者は生成前に決めて `audience` に書く。`request` も固定する。**対象読者・依頼は未決定。**
- 比較・統計用の `document_id` は台帳の `source_id`、理解問題用は抜粋IDにする（[接続の制約](public-document-evaluation.md#既存ツールとの接続)）。
- 行政文書群として独立に集計する。他の文書群や青空文庫と合算しない。
- 理解問題は「誰が」「どの条件で」「何を完了すべきか」を問い、根拠を抜粋内の引用にする。各抜粋に2問の草案があり、選択肢は同じ抜粋内の別の記述や、原文にない誤りを混ぜた。**正解の妥当性は人が原文と照合する。**
- 組織の責任分担が実務として適切かは評価しない。文書に書かれた責任が保たれているかだけを見る。

## 人が行うこと

1. 各 `candidate` について、台帳の本文を原本（Word と、あれば PDF）と見比べ、`correspondence` に確認者・確認日を記入する。
2. `third_party_content` と加工主体の表記を確認する。
3. `preserve` の各項目と `questions` を原文と照合し、`confirmed_by`・`reason`、`verified_by`・`verification_reason` を記入する。修正や削除をしてよい。
4. `dapt-acceptance` を変更不要の対照例にしてよいか判断し、`no_change_reason` を確定する。
5. 採用するものの `status` を `adopted` に変える。`--readiness` の出力が空になるまで繰り返す。
6. 対象読者・依頼を決め、`cases` JSON を作って[計画の手順](public-document-evaluation.md#手順)に進む。
