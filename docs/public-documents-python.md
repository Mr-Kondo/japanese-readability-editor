## 目的

技術解説の推敲で、例外条件・API 名・コード・否定・時点（バージョン）の限定を変えないかを調べます。

## 対象

出典は <https://docs.python.org/ja/3.12/> の4ページです。

## 取得で分かったこと

- 訳が揃っていない段落があります。ページ全体の本文段落（p・li・dd）のうち日本語を含む割合は、エラーと例外 97%、モジュール 100%、tempfile 76%、secrets 93%、venv 72%、hashlib 43% でした。英語のままの段落は日本語の読みやすさの評価対象にせず、除外として記録しました（`x-pye-p69-p71`、`x-pyt-p18-p31`）。venv は割合が低く、初回の候補から外しました。
- `tempfile` の一部の段落には、Sphinx の記法がそのまま残っています（`x-pyt-p8`）。また、文が崩れた訳（`x-pyt-p60`）があります。原文の不備と推敲の差を区別できないため、除外しました。訳文の不備は評価と別に扱います。
- 抽出で次を失います。強調（太字・斜体）、リンク先、図、段落の入れ子の見た目。コード中の `>>>` と `...` は残します。強調が意味を持つ箇所（例: `secrets` の「復元可能な形式でパスワードを保存 してはいけません」）は、強調が失われている点を人が確認します。
- 抽出は `tools/extract_html_text.py` です（標準ライブラリのみ）。本文の範囲は `div[role=main]` を指定しました。段落の識別子（`P<連番>`）が抜粋範囲（`locator`）です。離れた段落は `P51-P52,P55-P56` のように書きます。

## 抜粋の選び方と分割

選定基準は台帳の `groups.python-docs-ja.selection` に記録しています。その抜粋だけで、手順・条件・例外・戻り値や副作用・禁止や推奨のいずれかが読めるものを選びました。選び方は、各ページを段落単位で抽出し、「場合」「ただし」「ない限り」「してはいけません」「べき」「なければなりません」等を含む段落を走査して、トピックが重ならないよう選ぶ方法でした。走査した全段落は記録していません。**手作業の選定であり、無作為抽出ではありません。**

| 側 | 出典 | 抜粋 | 主な内容 |
|---|---|---|---|
| 調整用 | モジュール、`tempfile` | 10件 | 検索パス、キャッシュ、`-O`、一時ファイルの安全性と削除責任 |
| 最終評価用 | エラーと例外、`secrets` | 8件 | try/finally の順序、raise と連鎖、with、乱数とパスワード保存 |

分割はモデル出力の生成・閲覧の前に決め、台帳に日付付きで記録しました。限界は次のとおりです。

- トピックと分割が交絡します（調整用はモジュールと一時ファイル、最終評価用は例外と暗号乱数）。
- 全て同じ文書（Python 3.12 日本語版）で、著者・翻訳チームの偏りは抑えられていません。
- 独立した原本は調整用2、最終評価用2です。集計の信頼区間は意味を持たず、記述的な予備評価にとどまります。
- 変更不要の対照例は `pys-no-recoverable-password` です（評価前に私が判断したもので、人の確認が必要）。

## 保持要件

`preserve` の `kind` に、次の対応で記録します。いずれも抜粋内の引用（`quote`）と、人の確認者・理由が必要です。

| 保持するもの | `kind` | 補足 |
|---|---|---|
| コード・識別子・リテラル・インデント・コメント | `code` | 一字も変えない。英語のコメントも訳さない |
| 条件・順序（どの場合に何が先に起きるか） | `condition` | try/finally の順序、検索の順序 など |
| 例外・限定（その場合を除く） | `exception` | |
| 禁止・必須・推奨の強さ | `strength` | 「してはいけません」「しなければなりません」「べき」を弱めない |
| 注意・変更の可能性 | `warning` | 既定値が変わりうる、挙動を当てにしない |
| 数値・時点 | `number`、`claim` | 「2015 年の時点で 32 バイト」のように時点とセットで保つ |
| 主張・保証の範囲 | `claim` | 「保証はありません」「だけです」等の限定 |

`allowed_changes` には、許容する変更を書きます。草案では全項目に「文の分割・結合、語順や接続表現の整理（主体・条件・順序・義務の強さ・識別子・コード・数値・時点を変えない範囲）」としました。技術内容の更新と用語の置き換えは許容に入れず、不具合として評価します。

特に取り違えやすい箇所を保持要件にしました。例: 未処理の例外が「finally の後に再送出される」順序、`from None` が連鎖を「無効にする」こと、`-O` と `-OO` の違い、キャッシュを確認しない2つの場合、`dir` が `None` のときの挙動、ファイル名に扱いやすい性質の「保証はありません」。

## 評価の設定

- モードBを明示し、対象読者は生成前に決めて `audience` に書く。`request` も固定する。**対象読者・依頼は未決定。**
- 比較・統計用の `document_id` は台帳の `source_id`、理解問題用は抜粋IDにする（[接続の制約](public-document-evaluation.md#既存ツールとの接続)）。
- 技術文書群として独立に集計する。他の文書群や青空文庫と合算しない。
- 理解問題は抜粋の記述から答える形にし、一般的な Python の知識だけで正解できる問いに偏らせない。ただし、選択肢の妥当性と正解は人が原文と照合する。
- 技術内容の現行最新版との一致は評価しない。文書の採用は、現行最新版であることの保証ではない。

## 人が行うこと

1. 各 `candidate` について、台帳の本文を原本（ページ）と見比べ、`correspondence` に確認者・確認日を記入する。強調の欠落と、HTML と `.po` の差も見る。
2. 利用条件の表記と `third_party_content` を確認する。
3. `preserve` の各項目と `questions` を原文と照合し、`confirmed_by`・`reason`、`verified_by`・`verification_reason` を記入する。修正や削除をしてよい。
4. `pys-no-recoverable-password` を変更不要の対照例にしてよいか判断し、`no_change_reason` を確定する。
5. 採用するものの `status` を `adopted` に変える。`--readiness` の出力が空になるまで繰り返す。
6. 対象読者・依頼を決め、`cases` JSON を作って[計画の手順](public-document-evaluation.md#手順)に進む。
