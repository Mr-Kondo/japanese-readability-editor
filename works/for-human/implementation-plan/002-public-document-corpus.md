# 公開文書による評価データの準備計画

## 要点

- Issue #38 で決めた計画である。実在する公開文書で、意味を保った改善と、不要な変更をしない判断を調べる。
- 公開文書は正解ラベル付きのデータではない。既存の人工例に加える予備評価であり、効果は未測定である。
- 文書群は5つで、P0 が4群、P1 が IPA の資料群である。青空文庫は補助群で、業務・技術文書と合算しない。
- 候補は計93件である。人が確認して採用したものは0件で、生成・評価・自動指標（#45）は未実行である。

## 目的

公開文書で、意味を保った読みやすさ改善と、不要な書き換えを避ける判断を評価できるデータを準備します。

### 手順

```mermaid
  A["資料を planned で登録"] --> B["収集し版とハッシュを記録"]

  D --> E["adopted か excluded を記録"]
  E --> F["検証して cases を作成"]
```

### 共通ルール

- 台帳 `evals/public-documents/manifest.json` に、資料、抜粋、保持要件、質問、分割をまとめて記録する。
- 原本はリポジトリに保存しない。取得元と SHA-256 で識別し、版は release、commit、取得時点で示す。
- 本文を載せるのは、`redistribution: allowed` の資料だけである。
- 抜粋は各群で約10件を目安にする。統計的な十分性の根拠ではない。候補は生成結果を見る前に登録する。
- 変更しない対照例を各群に入れる。原文をそのまま返すことは失敗ではない。
- `tuning` と `final` は原本単位で分ける。調整に使った抜粋は、スキル改良（Issue #44）の後の最終評価に使わない。
- 採用する抜粋の保持要件には、確認者の名前と理由が必要である。LLM の判定は補助であり、保持要件や正解の定義には使わない。

### 検証と既存ツール

- 検証は `tools/validate_public_corpus.py` が、形式と整合だけを見る。保持要件の意味、利用条件の解釈、抜粋と原本の対応は、人が確認する。
- 既存の比較・統計・理解問題のツールには、`document_id` の数え方に制約がある。使い方は原文に従う。
- 比較と理解問題は Mode B だけに使い、小説（Mode D）や現代化は採点しない。

## 限界・未確認

- 人の確認と採用は未実施である。保持要件と理解問題は助手の下書きである。
- 公開文書が学習データに含まれたかは不明である。結果を社内文書へ当てはめない。
- 社内業務での効果保証、自律的なスキル更新、学習データに含まれないことの証明、改善率の事前予測は範囲外である。
- NTT の資料（非営利・相続の条件）、PostgreSQL 日本語版（他媒体利用の注意）、BCCWJ は初期範囲から外す。使うには利用条件を別途確認する。
