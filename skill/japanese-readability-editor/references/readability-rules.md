# 日本語可読性ルール詳細

`SKILL.md` の診断の順序を、各段階の「見る点」「直し方」「直さない場合」に分けて説明する。判断に迷うときだけ読む。

設計の出典は次の6つである。文章は転載せず、原則と手順として再構成している。

1. Qiita「日本語文章の可読性改善」(masakai)。段落・文の長さを先に見る診断順序と、測定指標の考え方。
2. Zenn (ncdc)。直訳調と複雑な文構造の検出、書かせる前の論点整理。
3. Zenn (lotation)。読者が次の文を予測しながら読めることを軸にした、AI特有の癖の一覧。
4. GitHub の coji/natural-japanese(MIT)。語順、読点、接続詞の射程、否定の入れ子、列挙の埋没、語形の重さの整理と、実文書での閾値の校正結果。太字を文中の要点に限ること。見出しと各段落の先頭文だけを読んで、論旨を確かめる手順。同リポジトリは、本多勝一、木下是雄、石黒圭、結城浩らの作文技術書を出典としている。
5. GitHub の nanaism/yomiyasu(MIT)。書き換えで保つものとしての「比重」と「言い切りの強さ」。太字が表示されない書き方と、その直し方。定着した慣用句を残す目安と、比喩の含みを残すこと。結論や警告を伝える見出しを薄めないこと。定型の結び。
6. GitHub Gist の k16shikano/japanese-tech-writing(Unlicense)。推量や可能性を、根拠なく断定へ変えないこと。太字を論理の要所に限ること。翻訳調の比喩を見分ける二段階の判定。説明の中で読者を「あなた」と呼ばないこと。

製品の仕様やインストール方法は、これらではなく各ベンダーの公式資料に従う。

## 0. 大前提

- 目的は「意味・精度・必要な情報量を維持したまま、読者の認知負荷を下げる」ことである。短くすること自体は目的ではない。
- 次の情報は、読みやすさを理由に削除・簡略化・言い換えしない。数値と単位、条件、例外、因果関係、主体、固有名詞、技術用語、API名、コマンド、コード、URL、引用、citation、出典。
- 情報密度を落とすことと、可読性を上げることは別である。削った結果、読者が推測しなければならなくなるなら、可読性は下がっている。
- 原文にない情報を足さない。数値、事例、留保、断定を、推測で補わない。
- 利用者に確かめるべき箇所で、確かめられないとき(本文だけを求められたとき、対話できない環境など)は、その箇所だけ元の表現を残す。確かめる代わりに、もっともらしい中身を作らない。ほかの箇所は、通常どおり直す。
- 条件の範囲を変えない。「それ以外の場合」のような残余の条件を、具体的な条件に言い換えると、範囲が変わり、抜けるケースが生まれる。
- 言い切りの強さを変えない。推量(「〜だろう」「〜かもしれない」)や可能性を断定にしない。断定を推量に弱めない。原文にない「できる」「必要がある」「べき」を足さない。断定に直せるのは、本文の中の根拠で命題が確定している場合だけである。
- 比重を変えない。何を一番大事とし、何を軽く扱っているかを保つ。否定していたもの(「AではなくB」のA)を、並列(「Aに加えてB」)や順位(「AよりB」)に変えない。並列していたものに、順位をつけない。
- 文体(常体と敬体)は、原文に合わせる。利用者が求めない限り変えない。
- 文を分けて字数が増えるのは、正しい結果である。字数が増えたことを、不合格の理由にしない。
- 指摘は、見直しの起点であり、命令ではない。読んで引っかからない文は、直さない。
- 同じ種類の修正を、文書全体へ一律に当てない。自然な濃淡まで消えて、かえって不自然になる。読者に価値を足せる箇所だけを直す。
- 直した後は、元の文章と事実・条件・数値が変わっていないかを確認する。

## 1. 内容と論点の整理

見る点:

- この文章は誰が何のために読むのか。
- 結論は何か。結論が最後まで出てこない構成になっていないか。
- 一つの段落や節に、複数の論点が混ざっていないか。
- 読者は、何を知っていて(知識)、どれだけ読む気があり(意欲)、何のために読むのか(目的)。専門用語を説明なしに使ってよいか、どこまで詳しく書くかは、この3点で決まる。

直し方:

- 論点ごとに段落や節を分ける。
- 技術文書と業務文書では、How より先に What を示す。
- 順序の入れ替えで済むなら、新しい説明を足さない。

素材の不足に気づいたとき:

- 固有名詞、数値、実例がなく、一般論だけで済んでいる段落がある。これは書き方ではなく、素材の不足である。
- 言い回しを直し続けても解決しない。利用者へ、必要な素材を求める。
- 原文にない数値や事例を、推測で足さない。

直さない場合:

- 利用者が「文言は変えずに」「段落だけ」と指定している。この場合は論点の再構成もしない。

### 見出し

見る点:

- 見出しと各段落の先頭文だけを順に読んで、文章の内容を追えるか。追えない箇所では、見出しか段落の冒頭に問題がある。
- 見出しだけで、その節が何を扱うのかが分かるか。「背景」「概要」「メリット1」「注意」のようなラベルや、「〜しませんか」のような呼びかけだけでは、節を読むまで中身が分からない。

直し方(書き換えを許すモードのみ):

- ラベルや呼びかけだけの見出しは、その節で扱う対象が分かる句にする。語は本文から取る。本文にない主張や評価を、見出しで足さない。
- 結論や警告を伝えている見出し(「本番環境では `--force` を使わない」など)は、一般的な題名(「`--force` オプション」など)に薄めない。
- 疑問形の見出しは、その節が問いに答えているなら残す。疑問形か断定形かは問わない。問うのは、扱う対象が分かるかである。
- 手順の番号のように、順序や参照に使う番号は残す。
- 見出しの書き方を、文書全体で一律にそろえない。直すのは、中身が分からない見出しだけである。

直さない場合:

- Paragraph-only モード。見出しも変えない。

## 2. 長すぎる段落

目安は200字以上である。スマートフォンの画面で1段落が画面を埋めるくらいの量が、一つの基準になる。合否基準ではない。

見る点と手順:

1. 文章を書き換えず、話題の境界で段落だけを分けられないか。
2. 分けられるなら、改行と空行だけを挿入する。文言、語順、句読点、接続詞、情報は変えない。
3. 分けても各段落が長いまま、または境界が見つからない場合だけ、書き換えを検討する。

典型的な話題の境界:

- 事実 → 解釈
- 問題 → 原因
- 原因 → 対策
- 現状 → 例外
- 原則 → 例
- 結論 → 補足
- 操作 → 結果
- 問題提起 → 解決

段落の偏り:

- 改行のないまま1000字を超える「壁」は、視覚的な休憩点を奪う。
- 1文ごとに段落を分ける「細切れ」は、つながっているはずの論理を寸断する。

段落の冒頭(書き換えを許すモードのみ):

- 段落の冒頭で、その段落の話題が分かるようにする。読者は冒頭で話題を予測し、その枠で残りを読む。
- 話題が末尾にあり、読み終えてから解釈をやり直す構成は、順序の入れ替えで直せないか確かめる。
- Paragraph-only モードでは、文の順序も入れ替えない。

直さない場合:

- 一つの手順や一つの仕様の説明で、途中で切ると読者が前提を見失う。
- 引用、ログの説明、数式の説明で、長さが内容の性質である。

## 3. 長すぎる文

目安は80字以上である。主語と述語の距離が開き、頭に入りにくくなる長さの目安になる。合否基準ではない。

読点を足して数字を合わせる修正は禁止する。分割した結果として読点が増えるのはよいが、読点の数が目的になってはならない。

目安の根拠:

- 参考として、coji/natural-japanese の校正結果を挙げる。AI が生成した業務文書241本(9,889文)の文長は、中央値が44字、p90が86字だった。80字以上の文は12.8%だった。
- 130字以上の文は、ほぼ全件が分割で読みやすくなった。90〜105字の帯は、直すかどうかの判断が最も割れた。
- 同リポジトリの追試では、人間が書いた技術記事10本(379文)の文長は、中央値が37字、p90が67字だった。
- このコーパスは、AI 生成の文書が中心で、書き手にも偏りがある。一般の基準ではない。80字は「候補」であり、80〜105字は文脈で判断する、という運用の根拠として読む。

見る点:

- 主語、述語、修飾、条件、例外、原因、結果、並列している情報。
- 主語と述語の間に何が挟まっているか。
- 一文に、独立した複数の事実が入っていないか。一文一義を守れているかのほうが、文字数より効く。

避ける構造:

```text
主語
 └ 長い修飾
    └ 別の修飾
       └ 条件
          └ 述語
```

直し方:

- 独立した複数の事実は、文を分ける。
- 深い入れ子は、修飾を別の文に出す。先に結論を述べ、条件や理由を後ろに置く。
- 条件と例外は、本文の文として残す。省略しない。

埋もれた列挙:

- 読点で区切った同格の項目が一文に4つ以上ある場合は、箇条書きにするか、文を分ける。
- 項目が3つの場合は、文が長いときだけ候補にする。
- 読点の多い文は、読点の打ち方ではなく、列挙が一文に埋もれていることが問題である。読点の数を指標にしない。

直さない場合:

- 仕様の条件を一文で述べたほうが、条件どうしの関係が正確に伝わる。
- 固有名詞や正式名称が長いだけで、構造は単純である。

## 4. 主語・述語・修飾の構造

見る点:

- 主語と述語が対応しているか。文の途中で主語がすり替わっていないか。
- 修飾語が、どの語にかかるのか一度で分かるか。
- 名詞の連結が長すぎないか。

### 語順

日本語の読者は、述語が出る文末まで、係り受けを保留して読む。保留の負担を軽くする語順がある。

- 長い修飾語を先に、短い修飾語を被修飾語の直前に置く。
- 節(主語と述語を持つ修飾)は、句(単純な語句)より先に置く。
- 時間や場所は、大きな枠から先に書く。年、月、日の順にする。

```text
前: 新しい、社内の全拠点で共通に使える認証基盤を導入した。
後: 社内の全拠点で共通に使える、新しい認証基盤を導入した。
```

### 読点

読点は、構造の切れ目を示す記号である。息継ぎのために打たない。

- 長い修飾語が並ぶときは、その境界に打つ。
- 短い修飾語を先に置くなど、語順の原則に反するときは、その境界に打つ。
- 切れ目のない場所の読点は、読み手を止める。統語上の理由がない読点は、削る。

### 主語と述語の距離

- 主語から述語までが離れると、読み手は主語を記憶に保って読むことになる。
- 「〜な理由は」で始めて「〜します」で終わる、ねじれも起きやすい。
- 直し方は、文を分けることである。主語と述語を近づけ、対応を確かめる。

### 否定・条件の入れ子

二重否定(「できないわけではない」)や、入れ子になった条件は、読み手に真偽の計算を強いる。読解の負荷が最も大きい類型である。

- 直すときの事故も最も多い。原則として触らない。
- 畳むのは、肯定の言い換えを作り、元の文と同じ意味だと確信できるときだけにする。
- 「Aないとは限らない」は、Aであることがあると言っている。「Aとは限らない」は、Aであることを保証しない。この二つは、意味が逆である。
- 婉曲に断定を避けたい意図のある箇所は、そのまま残す。
- 条件の対応関係、例外、前提を落とさない。

直さないもの:

- 「〜ないと動かない」「〜なければ意味がない」は、必要条件の標準的な言い方である。
- 「〜なければならない」「〜ざるを得ない」は、義務の定型である。
- どちらも、読み手に符号の計算を強いない。

```text
前: この設定を外すと、負荷が増えないとは言えない。
後: この設定を外すと、負荷が増えることがある。
```

上の例で「負荷が増えない」と書くと、意味が逆になる。

```text
前: リトライ回数を増やしても、失敗率が下がらないとは限らない。
後: リトライ回数を増やすと、失敗率が下がることもある。
誤: リトライ回数を増やしても、失敗率が下がるとは限らない。
```

「誤」は、否定を1つ落としたために、意味が逆になっている。

## 5. 文と文の論理関係

見る点:

- 前の文と次の文の関係が、文末まで読まないと分からない。
- 接続詞がなく、原因と結果、対比、逆接が読み取りにくい。

使う接続語の例:

| 関係 | 例 |
|---|---|
| 原因 → 結果 | そのため、そこで |
| 対比 | 一方で、これに対して |
| 逆接 | しかし、ただし、ところが |
| 具体例 | たとえば |

注意:

- 接続詞を機械的に足さない。前後の関係だけで明白なら省略する。
- 接続詞は、読者の予測を助ける。予測を裏切る展開(逆接など)にこそ必要である。
- 段落だけを分けるモードでは、接続詞を足さない。
- 接続語ごとに、効力の及ぶ範囲(射程)が違う。「あるいは」は近い語句の並列を示す。「一方で」は、段落や文脈の単位の対比を示す。
- 対比になっていない二つを「一方で」でつなぐと、読み手は対比の対象を誤る。単に付け加えるなら「また」を使う。
- 「しかし」が続くと、本当の対立点が分からなくなる。射程の合う別の語にするか、一つにまとめる。
- 段落の冒頭が、ほとんど接続詞で始まっていないか。接続詞の多用は、予測を助けるどころか、読み手の予測を乱す。

## 6. 読者が次の展開を予測できるか

前の文を読んだ時点で、次の文が何の役割を持つかをある程度予測できる状態を目指す。

### 未解決の疑問

読者に期待させた内容へ、答えないまま別の話題に移らない。

- 問題を提示した → 原因、または解決策を続ける。
- 操作を書いた → 結果、または確認方法を続ける。
- 新機能を書いた → 用途、または効果を続ける。

新しい説明を足すより先に、既存の情報の順序を入れ替えて解決できないかを確かめる。

### 唐突な否定

「単なるAではない」「AではなくBである」「ただのAではない」は、読者がAを想定していないと、不要な否定になる。

- 読者がAを想定していないなら、Bを直接書く。
- AとBを実際に比較している文脈では維持する。
- 否定を使うなら、Aが想定される背景を先に示す。

### 温度感

問題を述べる文と解決を述べる文が、同じ調子で並ぶと、どこが問題でどこが解決か分かりにくい。問題は「必要」「できない」、解決は「できる」のように、述語で区別できると読み進めやすい。

### 指示語

文脈から明らかな「この」「その」まで削らない。指示語は、前の文とのつながりを示す。

### 文末と文長の単調さ

- 同じ文末(「〜です。」「〜ます。」)が何文も続くと、内容が変わっていても、同じことの繰り返しに感じられる。
- 短い文と長い文を隣り合わせにすると、揃った長さを並べるより、注意を保ちやすい。
- 単調さは、順序や構造の問題が解決した後に、余力があれば直す。

## 7. 主体・視点の切り替わり

同一の段落で、次のような主体が切り替わる箇所を確認する。書き手、読者、利用者、開発者、担当者、システム、アプリケーション、LLM、AI Agent。

次の点を、読み手の推測だけに依存させない。

- 誰が判断するのか
- 誰が実行するのか
- 何が変化するのか
- 誰にとって改善なのか

直し方:

- 主体が切り替わる文では、主語を明記する。
- 切り替えが多い段落は、主体ごとに段落を分ける。

受動態の連続:

- 「〜と考えられている」「〜が求められている」が続くと、誰がしたのかが見えなくなる。
- 動作主が分かるなら、動作主を主語にする。分からない、または書けない場合は、そのままにする。

事実と意見:

- 事実は言い切る。推測や評価には、「〜と考えている」「〜の可能性が高い」のように、意見であることを示す。
- 境界がぼやけると、読者はどこまでが検証済みなのかを判断できない。
- 原文にない留保や断定を、足さない。原文が事実と意見を混ぜているときは、利用者に確認する。

## 8. 直訳調

検査する点:

- 英文の語順をそのまま維持した、長い修飾。
- 日本語として不自然な、動詞と目的語の組み合わせ。
- 名詞の過剰な連結。
- 過剰な名詞化。「〜の実施を行う」「〜に関する検討」など。
- 抽象名詞が中心の文。
- 「〜を実現する」「〜を提供する」の乱用。

英語の構文が透けて見える型の例:

| 型 | 直す方向 |
|---|---|
| 無生物が主語で、他動詞で結ぶ(「この結果は〜を示している」) | 人や状況を主語にする。「この結果から〜と分かる」 |
| 「〜することができる」 | 可能形か「できる」にする |
| 「〜することによって」 | 「〜すると」「〜して」にする |
| 「〜という観点から」 | 「〜で見ると」「〜については」にする |
| 「〜にとって重要」「〜にとって不可欠」 | 何が要るのかを具体的に書く |
| 抽象名詞を目的語にした「〜を持つ」 | 「〜がある」にする |
| 「それは〜である。なぜなら〜」 | 理由を一文にまとめる |
| 二重のダッシュで挟んだ挿入句 | 括弧にするか、文を分ける |
| 「〜する〜という〜な〜」のように重なる連体修飾 | 文を分ける |
| 英語の慣用句を直訳した動詞や名詞(「運ぶ」は carry、「開かれた問い」は open question、「露出する」は expose) | 9 の「比喩」の手順で判断する |

表の型を見つけても、機械的に置き換えない。その言い回しを選ぶ必然性が文脈にあるか、他の言い方のほうが自然でないかを、自問する。

直し方:

- 動詞に戻す。「検証を実施する」→「検証する」。
- 主語と述語を日本語の語順で組み立て直す。
- 名詞の連結は、助詞を補って読み下せる形にする。

直さない場合:

- 技術業界で定着したカタカナ語(キャッシュ、トークン、ワークフローなど)を、機械的に和語へ置き換えない。
- 引用や訳文の忠実さが求められる箇所。

## 9. AI的な抽象語・造語・万能動詞・比喩・語形の重さ

### 造語

その文章の中でしか意味が通じない「抽象名詞 + 抽象名詞」型の造語を、安易に使わない。具体的な動作や対象に言い換える。

言い換えてはいけないもの:

- 業界標準用語
- 学術用語
- 技術用語
- 製品名
- 文書内で明確に定義された用語

### 万能動詞

次の語は使用禁止ではない。具体性を隠していないかを確かめる。

効く、支える、重ねる、つなぐ、生む、高める、促す、作用する、機能する、置く、実現する、提供する

確認の手順:

1. 「何をするのか」が書かれているか。
2. 「その結果、何が変わるのか」が書かれているか。

例として、「再試行が安定性に効く」は、「通信が失敗しても再試行するため、一時的な障害でジョブが止まらない」のように、実際の処理と結果で書ける。

### 比喩

AI が書いた文章には、日本語として定着していない比喩が混ざりやすい。次の3種類がある。

- 英語の慣用句を直訳したもの(「ログが原因を運ぶ」は carry、「開かれた問い」は open question)
- 無生物に意志を持たせるもの(「データが語る」)
- 名詞を別の物にたとえるもの(「設定ファイルの迷路」)

判断の手順:

1. 初めて読む人が、字義どおりの動作や物を思い浮かべうるか。思い浮かべうるなら、比喩を疑う。
2. 主体と対象を、具体的な語で言い直せるか。言い直せるなら、その言い直しを書く。
3. 言い直せないなら、その比喩が何を指すのかが決まっていない。中身を推測で補わず、利用者に確かめる。確かめられないときは、元の表現を残す。

直さないもの:

- 定着した慣用句(「骨が折れる」「手を焼く」「目から鱗が落ちる」)。目安は、AI が広まる前の人の文章でも、普通に見かける言い方かどうかである。見かけるなら残す。
- 業界で定着した比喩の用語(「ボトルネック」「技術的負債」「ウォーターフォール」)。技術用語として扱う。
- コピーライティング、演説、創作の比喩。

含みを残す:

- 比喩や副詞を言い換えても、それが伝えていた評価の向きは残す。「地味に」は目立たないが確かにあること、「ようやく」は待っていたこと、「〜てしまった」は意図しなかったことを伝える。
- 比喩を消すために、元にない効果、数値、原因を足さない。

### 語形の重さ

- 漢字が7字以上続く箇所は、読点や助詞で開けないか確かめる。「初回課金転換率」のような、圧縮された漢語である。
- 固有名詞、法令用語、文書内で定義された用語は、開かない。分解できない名前は、書き手が直せる読みにくさではない。
- 名詞と「の」が3回以上つながる文は、どこかを動詞にして開く。動作を名詞に固めた「〜の実現」「〜への寄与」が原因のことが多い。
- 業務用の横文字が一文に密集し、意味の輪郭が曖昧なときは、具体的な語にする。定着した技術用語は、対象外である。

## 10. 冗長表現

削減候補:

- 不要な導入
- 同じ結論の繰り返し
- 各節の末尾で毎回同じ内容をまとめる文
- 「重要です」だけの評価文
- 「有効です」だけの評価文
- 読者がすでに理解できる内容の言い換え
- 内容のない締めの文
- 不要な一般論
- クッション語の積み重ね。「設定することができます」「〜という形になります」「〜的な部分」

削ってはいけないもの:

- 必要な条件、例外、前提。
- 評価文に見えても、なぜ重要なのかの理由を含んでいるもの。理由があるなら、評価語ではなく理由を残す。

クッション語は、辞書で一括置換しない。上手な人間の文章にも、かなりの割合で現れる。文脈を読んで、削っても意味が変わらない箇所だけを直す。

## 11. 広告調・AI決めぜりふ

通常の技術文書と業務文書では、次のような表現を、内容がないまま文章を締めるためだけに使わない。

- これが本質です
- 成功の鍵は〜です
- すべてはここから始まります
- 本当に重要なのは〜です
- 〜と言えるでしょう
- 〜なのです
- 「ポイントは3つあります」だけで、内容を予告する数宣言
- 「手作業の設定を、一度きりの作業へ。」のように、読点で間を置き、述語を書かずに助詞で言い切る決めぜりふ

直し方は、その文が伝えようとしている事実を、具体的に書くことである。伝える事実がないなら削る。「〜を、〜へ。」の型は主張を含むので、削らずに、原文から分かる述語まで書く。述語が原文から分からないなら、推測で補わず、利用者に確かめる。確かめられないときは、元の形で残す。

### 読者への呼びかけ

技術文書と業務文書では、次を見直す。

- 内容のない定型の結び。「いかがでしたか」「ぜひ試してみてください」「参考になれば幸いです」。伝える事実がないなら削る。
- 結びや呼びかけは、削るか残すかを決める。原文にない行動や手順(「まずは、〜を一つ書き出してみてください」)に書き換えない。具体的に見えても、原文にない情報を足している。
- 説明の中で、読者を「あなた」と繰り返し呼ぶ書き方。主語を省くか、本文から分かる役割名(「利用者」「開発者」)にする。役割名が本文から分からないときは、残す。

残すもの:

- 読者に具体的な操作を頼む文(「設定した後に、`doctor` を実行してください」)。呼びかけではなく、手順である。
- 原文の文体。結びを削っても、敬体を常体にしない。

例外: コピーライティング、演説、創作の文章。

## 12. 漢字・表記

最後に確認する。補助指標にとどめる。

- 漢字率を特定の数値に合わせることを目的にしない。
- 固有名詞、技術用語、学術用語を、読みやすさのために不自然にひらがなへ変えない。
- 参考値として、1979年の国語研究所の調査では、漢字が約26.5%、ひらがなが約57.3%、平均文長が約44字、1文あたりの読点が約1.74個だった。これは合否の基準ではなく、ずれの方向を見る参照点である。
- 段落と文の問題を直した後で、なお字面が詰まって見える場合にだけ、漢字をひらくことを検討する。

表記の統一:

- 表記ゆれ(「サーバ」と「サーバー」、「行う」と「行なう」)。
- 句読点のスタイルの混在(「、。」と「，．」)。
- 数字の全角と半角の混在。
- 同音異義語の誤用。
- 文書の中で多数派の表記に合わせる。引用、コード、固有名詞は、触らない。

### 太字

使う箇所:

- 太字は、誤読を防ぐ否定、手順の中の警告、節の結論のような要点にだけ使う。目安は、一つの節に1〜2箇所である。合否基準ではない。
- 太字が多いと、どこが要点なのか分からなくなる。多いときは、要点だけを残して外す。どれが要点か判断できないときは、残す。

表示される書き方:

CommonMark では、`**` のすぐ内側が記号(「」『』()、。:% やバッククォートなど)で、すぐ外側が文字(かな、漢字、英数字)だと、`**` は太字の区切りにならない。太字にならず、`**` がそのまま表示される。日本語では、括弧ごと太字にしたときと、句点まで太字にしたときに起きやすい。

```text
前: 次に**「文書の立場」**を決めます。
後: 次に「**文書の立場**」を決めます。

前: これは**必須です。**詳しくは下に書きます。
後: これは**必須です**。詳しくは下に書きます。
```

残す太字は、次の順に直し方を検討する。

1. 括弧ごと太字にしているときは、括弧の内側だけを太字にする。
2. 太字の終わりに句点、読点、コロンがあるときは、それを太字の外に出す。
3. 1と2で直せないとき(コードで始まる・終わる太字、括弧が二つ以上ある太字など)は、その太字が必要かを見直す。残すなら、`**` の外側で文字に接する側に、半角スペースを1つ入れる(例: `立場は **「勧め」か「決まり」** で決めます。`)。

直さない場合:

- Paragraph-only モード。`**` の位置を動かすと、空白以外の文字が変わる。直さずに、利用者に報告する。
- コードブロックやインラインコードの中の `**`。太字の記法ではない。
- 元から表示される書き方の太字。書き方だけを変える修正を、増やさない。

## 13. 新規生成時の準備

新しい文章を書く前に、次を整理する。利用者に見せる必要はない。

1. 読者(知識、意欲、目的)
2. 読者が必要とする情報
3. 結論
4. 結論を支える事実
5. 次に読者が知りたくなる事項
6. 不要な背景

書いた後で、上の診断を順に適用する。技術文書と業務文書では、How より先に What を示す。一次情報(コード、設定値、数値)は、要約せずに引用する。

固有名詞、数値、実例が手元に乏しいまま書き始めない。素材が足りないときは、利用者に求める。

## 14. スクリプトの読み方

`scripts/measure.py` は、次の指標を機械的に数える。

- 総文字数、漢字率、ひらがな率
- 段落数、平均段落長、200字以上の段落数
- 文数、平均文長、80字以上の文数、1文あたりの平均読点数

`--locate` を付けると、候補の位置(ファイル名、行番号、長さ、冒頭)を示す。

`--extras` を付けると、長さとは別に、読み流すと見落としやすい4種類の箇所を指摘する。

- 漢字が7字以上続く箇所
- 名詞と「の」が3回以上つながる箇所
- 二重否定
- 表示されない太字。Markdown のファイルだけを調べる。何を記号とみなすかは実装で違うため、GitHub と、CommonMark 0.31 に従う実装(pandoc など)のどちらか一方で `**` がそのまま表示される箇所を拾う。`**★重要**` のように、GitHub では表示される書き方も含む。

指摘は判定ではない。固有名詞や法令用語も拾うので、読んで引っかからない箇所は直さない。

数える対象から、fenced code block、YAML frontmatter、URL、Markdown の記号を可能な範囲で除く。Markdown のリンクは、表示テキストを文章として残し、URLを除く。

数値は候補の抽出に使う。修正するかどうか、どう直すかは、この文書の基準で判断する。スクリプトは意味を理解しない。

### スクリプトを使えない環境での目視

1. 画面いっぱいに文字が詰まった段落を探す。200字を超えていそうな段落が候補である。
2. 一度で読み切れない文を探す。80字を超えていそうな文が候補である。
3. 「ないわけではない」のような二重否定、「の」が3回以上続く文、漢字が長く続く語を探す。
4. 太字の `**` のすぐ内側に括弧や句点があり、すぐ外側に文字がある箇所を探す。
5. 見つけた箇所ごとに、直すか、残すかを決める。残す場合は、理由を一言で言えるようにする。

### 書き換えの前後の比較

`scripts/compare_rewrite.py` は、書き換えの前後を比べ、意味が変わったかもしれない箇所を挙げる。`SKILL.md` の「書き換えた後の照合」を、機械で補助する。

```bash
python3 scripts/compare_rewrite.py before.md after.md
```

| 指摘 | 意味 | 確かめること |
|---|---|---|
| numbers、urls、code、terms | 数値、URL、コード、用語の候補が、消えた(missing)か、増えた(added) | 削ってはいけないものを削っていないか。原文にないものを足していないか |
| unmatched の no source | 書き換え後の文に、対応する元の文がない | 原文にない情報を足していないか。結びを、原文にない行動に書き換えていないか |
| unmatched の no rewrite | 元の文に、対応する書き換え後の文がない | 必要な情報を削っていないか |
| markers | 否定、推量、可能、義務、依頼、勧誘、強調、限定、残余の条件の表現が、対応する文のあいだで増減した | 真偽、言い切りの強さ、条件の範囲、文の働きが変わっていないか |
| style | 敬体と常体のどちらが多いかが変わった | 文体を変えていないか |

指摘は判定ではない。正しい言い換えでも、語や表現が変われば拾う。たとえば、二重否定を正しく肯定に畳むと、否定は減る。挙がった箇所を元の文と見比べ、意味が同じなら、そのまま残す。

文の対応は、語の重なりで推定する。語順の入れ替えと、2文までの分割・統合には対応する。大きく言い換えた文は、意味が同じでも、対応がないと出ることがある。

SudachiPy と辞書(sudachidict-core か sudachidict-small など)が入っていれば、形態素解析を使う。否定を品詞で数え、「なくなる」「情けない」を否定に数えず、「迷わず」「ざるを得ない」を数える。カタカナ語の表記ゆれ(サーバとサーバー)は、同じ語とみなす。英数字の語は、カタカナの読みに置き換えずに比べる。

SudachiPy が入っていなければ、標準ライブラリだけで動き、出力の `tokenizer` が `regex` になる。入れるかどうかは、実行環境で決める。

- 会話ごとに作られる使い捨ての実行環境(ChatGPT や Claude のアプリなど)では、入れてよい。`python3 -m pip install sudachipy sudachidict-small` を一度だけ試す。ネットワークがなく入らなければ、`regex` の結果を使う。
- small の辞書は、core の約半分の大きさである。`assets/examples.md` の修正例では、core と同じ指摘になった。
- 利用者の手元の環境(Codex、Claude Code、Gemini CLI など)には、断りなく入れない。`uv run scripts/compare_rewrite.py` も、SudachiPy を取得して入れるので、同じ扱いにする。
- 手元で使うには、利用者が先に入れておく。Codex のサンドボックスのようにネットワークのない環境では、実行中には入れられない。

## 15. 直した後の自己点検

- [ ] 数値、条件、例外、因果関係、主体が、元の文章と変わっていない。
- [ ] 固有名詞、技術用語、API名、コマンド、コード、URL、引用、出典が変わっていない。
- [ ] 原文にない情報、留保、断定を足していない。
- [ ] 言い切りの強さ(断定、推量、可能)が、原文と同じである。
- [ ] 比重が、原文と同じである。否定していたものを並列や順位にしていない。
- [ ] 二重否定や入れ子の条件を畳んだ箇所で、真偽が反転していない。畳めないなら、触っていない。
- [ ] 「それ以外の場合」のような残余の条件を、具体的な条件に言い換えていない。
- [ ] 文体(常体と敬体)が、原文と同じである。
- [ ] 短くすることを目的にして、必要な情報を削っていない。
- [ ] 200字と80字を、合否基準として扱っていない。
- [ ] 接続詞を機械的に足していない。
- [ ] 残した太字が、表示される書き方である。
- [ ] 比喩を言い換えた箇所で、含みが残っている。言い直せない比喩に、推測で中身を補っていない。
- [ ] 見出しに、本文にない主張を足していない。結論や警告を伝える見出しを、薄めていない。
- [ ] 結びや呼びかけを、原文にない行動や手順に書き換えていない。
- [ ] 利用者に確かめられなかった箇所を、推測で書き換えていない。
- [ ] 読者に期待させた疑問に、答えている。
- [ ] Paragraph-only モードでは、空白以外の文字が変わっていない。
- [ ] `compare_rewrite.py` を実行できる環境では、挙がった候補を1つずつ確かめた。
- [ ] 直した箇所が、新しい問題を生んでいない。

## 16. 直しても再発するとき

同じ箇所を直しても同じ形に戻る、または似た問題が繰り返し出る場合は、その一文をこれ以上言い換えない。次のどちらかにする。

- 「残す」と決め、その形が文書に必要な理由を書く。
- 文や段落の構造を組み直す。語順の入れ替え、文の分割や統合、視点の変更などである。

回数で機械的に打ち切る規則ではない。同じ箇所が同じ形で再発するという状態が、単発の言い換えでは扱えないという合図である。

## 17. 作業ファイルの扱い

Paragraph-only の検証や、書き換えの前後の比較に使う元ファイルなど、作業中に作った中間ファイルは、利用者のプロジェクトに残さない。

- 対象の文書と同じディレクトリには置かない。環境のスクラッチ領域か、一時ディレクトリに置く。
- 検証が終わったら、中間ファイルを削除する。
- 利用者のプロジェクトに残すのは、完成した文書だけにする。
