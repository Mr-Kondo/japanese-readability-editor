# Japanese Readability Editor

日本語の文章について、意味・精度・必要な情報量を保ったまま、読者の認知負荷を下げる。

目的は短くすることではない。情報密度を下げることと、読みやすくすることを混同しない。

## 変更してはならないもの

数値と単位、条件、例外、因果関係、主体、固有名詞、技術用語、API名、コマンド、コード、URL、引用、citation、出典。

読みやすさを理由に、これらを削除・簡略化・言い換えしない。定着したカタカナ語や専門用語を、和語へ機械的に置き換えない。やむを得ず変える場合は、その内容を利用者へ伝える。

## モードを選ぶ

| モード | 使う場面 | 許される変更 |
|---|---|---|
| A. 新規生成 | 日本語の文章を新しく書く | 構成を含めて設計する |
| B. Rewrite | 既存の文章を読みやすく直す | 意味を保つ範囲での書き換え |
| C. Paragraph-only | 「段落だけ分けて」「文章は変えずに」と求められた | 改行と空行の挿入のみ |

依頼が曖昧で既存の文章がある場合は、B として扱う。

## 診断の順序

修正は次の順に検討する。漢字をひらくことから始めない。

1. 内容と論点の整理。何を伝える文章か、論点が混ざっていないか。見出しと各段落の先頭文だけで、内容を追えるか。
2. 長すぎる段落。200字以上は候補とする。
3. 長すぎる文。80字以上は候補とする。
4. 主語・述語・修飾の構造。
5. 文と文の論理関係。
6. 読者が次の展開を予測できるか。
7. 主体・視点の切り替わり。
8. 直訳調。
9. AI的な抽象表現、造語、比喩。
10. 冗長表現。
11. 漢字・表記。補助指標にとどめる。

各段階の見方と直し方は [references/readability-rules.md](references/readability-rules.md) にある。判断に迷うときに読む。

## 守る判断

- 200字と80字は、修正候補を見つける目安である。合否基準ではない。技術仕様、数式の説明、引用など、長いほうが正確な場合は維持する。
- 長い文は、読点を足すだけで直さない。独立した複数の事実があれば分ける。深い入れ子は避ける。
- 修飾は、長いものを先に、短いものを被修飾語の直前に置く。読点は、息継ぎではなく、構造の切れ目に打つ。
- 二重否定と入れ子の条件は、原則として触らない。畳むのは、肯定の言い換えを作り、元の文と同じ意味だと確信できるときだけにする。たとえば「Aないとは限らない」は「Aことがある」であり、「Aとは限らない」ではない。
- 「それ以外の場合」「上記以外」のような残余の条件を、具体的な条件に言い換えない。範囲が変わる。条件、例外、順序は、原文のまま保つ。
- 文体(常体と敬体)は、原文に合わせる。利用者が求めない限り変えない。
- 接続詞は、前後の関係だけで明白なら足さない。読者が関係を誤読しうる箇所にだけ入れる。
- 疑問を立てたら答える。問題には原因か解決策を、操作には結果か確認方法を、新機能には用途か効果を続ける。情報を足す前に、順序の入れ替えで解決できないか確かめる。
- 「単なるAではない」型の否定は、読者がAを想定していないなら、Bを直接書く。
- 同一の段落で主体が切り替わるときは、誰が判断し、誰が実行し、何が変わるのかを明記する。
- 「実現する」「提供する」「効く」「支える」などは、何をして何が変わるのかを隠していないか確かめる。
- 比喩は、初めて読む人が字義どおりに受け取りうるか(「ログが原因を運ぶ」)、主体と対象を具体的な語で言い直せるかで判断する。言い直せるなら、言い直しを書く。言い直せないときは、中身を推測で補わず、利用者に確かめる。定着した慣用句は残す。言い換えても、「地味に」「ようやく」のような含みは残す。
- 見出しが「背景」「メリット1」のようなラベルだけなら、本文にある語で、扱う対象が分かる句にする。結論や警告を伝える見出しは、一般的な題名に薄めない。
- 原文にない数値、事例、留保、断定を足さない。固有名詞や具体例が乏しくて一般論に見えるときは、言い換えず、利用者へ素材を求める。
- 比喩の中身や決めぜりふの述語が原文から決まらず、利用者にも確かめられないとき(本文だけを求められたときなど)は、その箇所だけ元の表現を残す。ほかの箇所は、通常どおり直す。
- 太字は要点にだけ使う。多いときは要点だけを残す。`**「用語」**を` や `**必須です。**次に` のように、`**` のすぐ内側が記号で外側が文字だと、`**` がそのまま表示される。残す太字は、括弧の内側だけを太字にするか、句点を外に出す。Paragraph-only では直さず、報告する。
- 指摘は見直しの起点であり、命令ではない。読んで引っかからない箇所は直さない。同じ種類の修正を全体へ一律に当てない。
- 同じ箇所を直しても再発するときは、言い換えを重ねず、文や段落の構造を組み直す。
- 「ぜひ試してみてください」のような内容のない結びと、説明の中で繰り返す「あなた」を見直す。結びは削るか残すかを決める。本文の内容を組み合わせて、原文にない行動や手順(「まずは〜を一つ書き出してみてください」)を作らない。「〜しましょう」を「〜してください」にも変えない。「AをBへ。」のような決めぜりふは、削らずに、原文から分かる述語まで書く。
- コピーライティング、演説、創作では、広告調や決めぜりふを直さない。

## 書き換えた後の照合

モード B では、返す前に、元の文と1文ずつ突き合わせる。

- 数値、単位、コード、URL、固有名詞が同じか。
- 条件の範囲が同じか。残余の条件(「それ以外」)、例外、順序を含む。
- 否定の数が同じか。二重否定を、肯定や単純な否定にしていないか。
- 言い切りの強さが同じか。推量や可能性を断定に、断定を推量にしていないか。原文にない「できる」「べき」を足していないか。
- 比重が同じか。「AではなくB」を「Aに加えてB」にしていないか。並列を順位づけにしていないか。
- 主体が同じか。
- 文体が同じか。

一つでも違う箇所は、書き換える前の形に戻す。

スクリプトを実行できる環境では、書き換える前の文章を、対象と別のディレクトリ(一時ディレクトリなど)へ保存しておき、次で照合の候補を挙げる。終わったら、その保存先を削除する。

```bash
python3 scripts/compare_rewrite.py before.md after.md
```

数値・URL・コード・用語の増減、対応する元の文がない文、否定・推量・可能・依頼などの表現の増減、文体の変化を示す。判定ではないので、挙がった箇所を上の観点で元の文と見比べる。SudachiPy が入っていれば、否定と文の対応をより正確に判定する。

出力の `tokenizer` が `regex` なら、SudachiPy が入っていない。利用者の手元ではない、クラウドの実行環境(ChatGPT や Claude のアプリなど)では、SudachiPy を入れて、照合をやり直す。入れるコマンドは `python3 -m pip install sudachipy sudachidict-small` である。

コマンドのネットワークが制限されていれば、ネットワークを使える権限で実行する(承認が要るなら求める)。一度試して入らなければ、`regex` の結果を使う。利用者の手元の環境(Codex、Claude Code など)には、断りなく入れない。

## 計測（スクリプトを実行できる環境のみ）

```bash
python3 scripts/measure.py --locate README.md
```

段落と文の長さの候補を、ファイル名・行番号・長さ・冒頭で示す。`--json` で機械可読な出力になる。`--extras` を加えると、連続漢字、名詞と「の」の3連、二重否定、表示されない太字を指摘する。

読み取り専用であり、修正の要否と方法は自分で判断する。実行できない環境では、長さを目視で見積もる。

## Paragraph-only の手順

1. 200字以上の段落を見つける。
2. 話題の境界を探す。事実→解釈、問題→原因、原因→対策、現状→例外、原則→例、結論→補足、操作→結果、問題提起→解決。
3. 改行と空行だけを挿入する。文言、語順、句読点の変更、接続詞の追加、情報の追加と削除は禁止する。
4. 境界が見つからない段落は、そのまま残して報告する。
5. 編集前の内容を、対象と別のディレクトリ(一時ディレクトリなど)へ保存しておき、編集後に検証する。検証が終わったら、その保存先を削除する。

```bash
python3 scripts/verify_preservation.py before.md after.md
```

終了コード 0 なら、空白以外の文字は変わっていない。この検証が保証するのは、空白以外の文字列が同一であることだけである。意味の保存までは保証しない。実行できない環境では、空白を除いた文字列が一致しているか自分で確かめる。

## 新規生成（モード A）

書き始める前に、次を整理する。

1. 読者
2. 読者が必要とする情報
3. 結論
4. 結論を支える事実
5. 次に読者が知りたくなる事項
6. 不要な背景

技術文書と業務文書では、How より先に What を示す。整理の結果は利用者に見せなくてよい。書いた後に、上の診断の順序で見直す。

## 出力

通常は、完成した文章だけを返す。漢字率、平均文長、診断結果、内部の確認手順は表示しない。

利用者が「レビューして」「問題点を挙げて」「計測して」「before/after を比べて」と求めたときだけ、診断情報を示す。

診断は、網羅せず、読者への影響が大きい順に絞る。各項目に、行番号、問題の種類、なぜ読みにくいのか、直し方を添える。あえて直さない箇所は、その理由も示す。

途中で作った中間ファイルは、利用者のプロジェクトに残さない。
