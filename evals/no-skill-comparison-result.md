# スキルなしとの比較評価（#165）の結果

計画は [no-skill-comparison.md](no-skill-comparison.md)。実行記録は [no-skill-run/run.json](no-skill-run/run.json)（入力・指示・生出力・採点の生の判定・実モデル・費用）。実行は 2026-11-12。判定は **VALID**（実モデル `claude-sonnet-5-5` が全呼び出しで一致、欠落なし、点検用12項目は12/12が期待どおり）。

## 結論

- この12ケースとモデル採点では、事前に決めた読み方のとおり、skill は意味保持と読みやすさの両方で、none（スキルなし）と short（数行の指示）より優位だった。
- ただし、この結果は、スキルの規則に沿って作った入力と、その規則を含む採点基準での結果である。スキルなしより一般に良いことの証拠ではない（下の「読むときの注意」）。
- ただし、short に対する優位の大半は、依頼にない文体の保持（常体を敬体にしない）と、原文のまま返す判断で説明できる（下の「事後の分析」）。それらを除くと、short との差は小さい。
- 費用は、skill の生成が none の約40倍、short の約30倍（$2.22 対 $0.05、$0.07）。効果と費用の釣り合いは、この評価では判断しない。
- 上流 yomiyasu が公表した「スキルなしに読みやすさで負ける」という結果は、この評価では再現しなかった。ただし、入力が違いすぎて（上流は約1,500字の下書き、こちらは26〜66字の自作文）、比べられない。

## 事後の分析（事前登録にない。内訳の確認）

失敗の理由の文を、キーワード（「敬体・常体・文体」、「本文だけ」「二重」「説明を付け」）で機械的に3つに分けた。分類は人が全件を読んで確かめたものではない。none の失敗の理由は3件を、short の失敗の理由は11件の冒頭70字を読んだ。skill の失敗は1件で、読んだ。

| 群 | 文体の変更（常体を敬体に） | 本文以外の出力（説明の付加、二重の出力） | それ以外 |
|---|---:|---:|---:|
| none | 4 | 0 | 7 |
| short | 6 | 3 | 2 |
| skill | 0 | 0 | 1 |

- 12ケースのうち11ケースは、原文の文体（常体か敬体）を保つことを、採点の必須項目にしている。一方、12件の依頼文は、どれも文体に触れていない。none と short は、依頼にない文体の保持を満たせず、failになった場合がある。skill は、規則として文体を保つため、満たした。
- 文体の変更と本文以外の出力を除くと、none の失敗は 7 件、short は 2 件、skill は 1 件。skill と none の差は残る（7 対 1）。skill と short の差は、この内訳では 2 対 1 で、区別できない。short の指示は「文体を変えない」を含んでいたが、6件で守られなかった。情報の足りなさだけでは説明できない。short の本文以外の出力は、すべて r09（敬体の版と常体の版を並べ、説明を付けた）。
- 原文のまま返した出力は、skill が r07・r10・r12 の各3回（9件）、none と short は合わせて r07・r04・r10 の各1回（none 1件、short 2件。どちらがどれかは集計していない）（上の表の「原文のあるケース」は r05 を除く33件。r05 は資料から作るケースで、原文がない）。読みやすさで skill が勝った組のうち、skill が原文のまま返した出力が相手に勝った組は、none に対して1件、short に対して3件。skill が書き換えた出力同士では、none に9勝2敗、short に3勝1敗。
- skill の1件の失敗は r11 の1回目（原文にない因果の接続を足した）で、同じ回の none と short は pass だった。採点の判定理由には、意味は保たれているとも読める記述があり、判定が揺れている可能性がある。none と short の失敗の理由にも同様の揺れがあるかは、全件を読んでいないため分からない。

## 読むときの注意

- 12ケースは、スキルの規則が防ごうとする失敗（主体の創作、強さの変化、文体の変更など）を狙って作った自作文で、採点基準の必須項目と禁止項目も、その規則に沿っている。スキルに有利な出題である。結果は、スキルなしより一般に良いことを示さない。
- skill には依頼の先頭の「モード B。」を付けたまま渡した。この接頭辞は、書き換えの範囲（推敲か、資料からの作成か）を示すヒントで、none と short には渡していない。これも、スキルに有利な条件の一部である。
- short の指示は、README と description だけから書かせた。スキルの本文にある規則（例: 文体の扱いの細目）は読んでいない。
- 入力は26〜66字の短い文で、実際の文書の長さではない。読みやすさの判定は、未判定と同点が多い（none 11/23、short 16/23）。
- 採点は、生成と同じ系統のモデルによる。人の判断への校正はしていない。点検用12項目が全問正答だったことは、採点が極端に外れていないことを示すにとどまる。
- 生成は1ケース3回。独立した36種類の文章ではない。
- short は、1つの指示の1回の書き出し。書き方を変えると結果が変わりうる。

## 計画からの逸脱

- short の指示は、最初の出力が6行（前置き1行と番号つきの5項目）で、「5行以内」を1行超えた。生成の前に、再生成せず、その出力を採用すると決め、計画に記録した。
- runner の接頭辞の判定を、実行前に1回直した（「モード B。」の空白を許す）。出力の生成前で、結果への影響はない。

## この結果の使い方

- README と `docs/design.md` には、スキルの効果を一般に主張する書き方はない。この結果を理由に書き足さない。引用するときは、「自作12ケース・モデル採点では」と限定する。
- 費用が約30〜40倍違う。short に「文体を保つ」を足した指示との差は、この評価では測っていない。
- 次に確かめるべきこと: 実際の文書の長さでの比較。#38〜#44 の公開文書の評価データに、スキルなしの群を入れる。意味保持の差が、文体の保持に偏っているかも、依頼に文体を書いた版で確かめられる。
