# 意味の確認と、対象・条件・状態の照合

Issue [#107](https://github.com/Mr-Kondo/japanese-readability-editor/issues/107)の改良記録。公開する入力は、新規の[人工8ケース](meaning-confirmation-cases.json)だけである。

## 変更と確認観点

| 観点 | ケース | 確認すること |
|---|---|---|
| 不明な比較対象 | m01 | 対象を創作せず、その関係を質問する |
| 回答後の推敲 | m01のfollow_up | 回答を使い、報告・考察・結論・確認を保ち、同じことを再質問しない |
| 明確な関係 | m02 | 既知の対象を質問せず、通常どおり推敲する |
| 二つの状態 | m03 | 発送済みと発送不要の判断を区別し、終了条件を保つ |
| 本文のみ | m04 | 不明な部分は保持し、質問や作業注記を混ぜない |
| 意図的な曖昧さ | m05 | 二通りの読みを保ち、ほかの名詞化は直せる |
| 形式と必要条件の衝突 | m06 | 条件や形式を黙って変えず、調整点を質問する |
| 資料からの新規生成 | m07 | Aでも説明可能な状態と未解決事項を落とさない |
| 不要な質問の抑制 | m08 | 推敲に不要な主体は尋ねず、条件を保つ |

完成文の完全一致や、疑問符の有無だけを合否にしない。質問は不明な関係を特定しているか、文案は必要な主張を保つかを読む。

## 比較条件

- 基準は `928eea5`（v0.20.1）。変更前後の同じ3ファイル（`SKILL.md`、`references/readability-rules.md`、`assets/examples.md`）を入力する。
- Claude CLIの既存の呼び出し関数 `tools/evaluate_readability.py:invoke` を使う。ツールなしで指示をプロンプトに渡す確認であり、製品内のインストール済みSkillの実呼び出しではない。
- 各版で8ケースを1回ずつ、一つの文脈で生成する。m01は最初の応答と利用者の回答をプロンプトへ戻して次の応答を得る。永続的なホストセッションの再開ではない。
- 単発の本文だけを返す既存CLIの生成指示は、質問の評価に向かないため流用しない。呼び出し関数だけを使い、実際の入力、出力、モデル識別子、指示のハッシュを[実行記録](meaning-confirmation-run.json)に残す。
- 原文の欠落・追加、質問の前提、不要な再質問、形式の扱いを実装者が確認する。独立した盲検評価や人手評価とは区別する。

## モデル出力の確認結果

実行したモデルは `claude-sonnet-5-5`。各版の出力と、読み込ませた指示のハッシュを[実行記録](meaning-confirmation-run.json)に残した。`before`が変更前、`after`が初稿、`after_revision`が最初の補修後、`final`が公開する指示である。途中の出力を見て補修したため、同じ8ケースは開発に使用済みであり、未使用の評価データではない。

| 観点 | 観察した結果 |
|---|---|
| m01の最初の応答 | 旧版は比較対象を問い直さず文案を返した。新版は比較対象を質問した。ただし、初稿と補修後にも、未確定のまま残せる関係への追加質問があった |
| m01の回答後 | 各版とも利用者が示した比較対象を使い、報告・考察・結論・担当者間の確認を残し、比較対象を再質問しなかった |
| m02・m08 | 各版とも、明確な対象や推敲に不要な主体を質問せず文案を返した |
| m03 | 各版とも発送済みと発送不要の判断を区別した。今回の出力に状態の同一視は見られなかった |
| m04・m05 | 本文のみの指定と意図的な曖昧さを各版とも保った。最終版のm04は名詞化を残しており、読みやすさが改善したとは評価しない |
| m06 | 各版とも両立しない制約を質問した。旧版は、省けないと指定された条件の一部省略も選択肢に含めた。新版はその案を出さなかった。ただし、文数の変更だけで字数制約も解決するとは限らず、調整案の実現可能性は未確認 |
| m07 | 各版とも調査・修正・説明可能な状態と未解決事項を残した。最終版は主体を省略しているため、単独で転記する文案でも担当者が明確かは要確認 |

追加質問を抑えるため、未確定のまま残せる関係を尋ねないことを詳細手順へ補い、さらに入口と例にも判断基準を示した。最終出力では報告先や主体の質問はなくなったが、確認対象への質問が残った。**不要な質問を十分に抑えられたとは判定しない。** 今回確認できたのは、比較関係を問い直す挙動と、既存の意味保持・対照例の上記範囲である。

初回の`--safe-mode`を使った呼び出しは、モデルへのアクセスエラー（404）で生成できなかった。モデル名の明示でも解消しなかったため、両版を同じ`--setting-sources project`・ツールなしの条件へそろえて実行した。失敗した呼び出しを成功件数へ含めない。設定を変えた理由と実際のフラグは実行記録に残している。

## 構造・互換性の検証

変更前、入口文書の行数・版番号サンプルを修正した後、公開対象だけを取り出した最終状態の `tools/check_all.py` は、各1,025件中1,012件成功・13件スキップだった。入口の行数上限を変更せず、サンプルの版だけを新版へ同期した。

最終ソースで配布物を作り、ZIPの整合性、SHA-256、共通の指示・規則・例・版のバイト一致を確認した。隔離した配置先でv0.20.1を導入し、新版へ更新して、正本との厳密比較と同梱スクリプトの実行を確認した。その後、配置した4か所（Codex共通、Claude Code、Antigravity IDE、Antigravity CLI）を削除し、対象のSkillが残らないことを確認した。これらは配置・実行経路の確認であり、各製品のモデル挙動の確認ではない。

ホスト固有のコードと導入先は変えず、既存の `tools/install.py`、`tools/uninstall.py`、`tools/package.py` を使う。インストール済みの利用者のコピーは自動で更新しない。

既存の未コミット変更と非公開フィードバックを含めず、公開対象だけをステージして別の一時ディレクトリへ取り出す。配布物と導入確認も、このソースを基準に行う。公開差分では、非公開資料の固有語と、報告票の原文・結果の24文字連続一致がないことを確認する。この検査だけで機密情報が皆無とは保証せず、人工例を使用したことも目視で確認した。

## 限界

人工例を使った小規模な開発確認であり、未使用文書への一般化・成功率・利用者の理解度は測らない。ケースは同じ文脈を共有するため、独立した反復とは扱わない。比較で差がなければ、既存挙動を確認した結果として残す。

Windows実機、Codex・Claude Code・Gemini Antigravityでの今回の版の実呼び出し、独立した人手評価は別途の未実施事項である。構造検査・CI・配布物の一致だけで、それらを確認済みとしない。
