# 節で一つのメッセージに絞る規則の比較結果（見送り）

仮説・成功指標・撤退条件は [ADR](../adr/2026-11-11-section-single-message.md) に、実行前に書いた（ADR の本文のハッシュは実行記録に残していない。指標を後から動かしていないことは、記録だけでは第三者が確かめられない。結果の節の追記以外は、実行後に変えていない、という作業者の申告である）。ケースは [自作11ケース](section-single-message-cases.json)、実行記録と生の出力は [section-single-message-run/](section-single-message-run/) にある（`runner.py` が準備・生成・集計を行う）。

## 結論

**規則は足さない。** 旧版（v0.22.0、355a42e）と候補版（`readability-rules.md` に小節「節で伝える内容を一つに絞る」を足したもの）で、混在した節を分ける挙動に差が出なかった。差が出た1件は、候補の規則の例と同じ形に合わせた入力で、分けすぎと結びの掛かり先のずれが見えた。事前の成功指標のうち、分離（指標2）と保存（指標1）を満たさなかった。

## 実行条件

- 旧版・候補版とも、`SKILL.md` と `examples.md` は同一。違いは `readability-rules.md` の小節だけ（SHA-256 は `run.json` の `skill_sha256`）。
- 各ケース×各版×3回=66出力。`sonnet / medium`、ツールなし、新しい文脈（`tools/evaluate_readability.py` と同じ呼び出し）。実モデル識別子は全呼び出しで `claude-sonnet-5-5`、CLI は 2.1.319。
- 意味保持の採点は、生成66出力と既存の12対照を混ぜて6回に分けた。ペア判定は、両版で意味保持が pass した25ペアを、左右反転で2回判定する設計だった。

## 観察（片方向だけの判定と、出力の読み取り。事前の指標ではない）

- 主4ケースで、候補版は見出しを一つも足さなかった。s01（README の「使い方」に導入・設定・困ったとき・ログ保管が混在）は、両版とも3回とも原文のまま返した。s11（項に通知と当番運用が混在）は、段落だけを分けた。
- s04（保守作業と経費精算が一つの「お知らせ」に混在）だけ、候補版は3回とも見出しを増やした。出力は「保守作業」「経費精算」「お問い合わせ」の3節で、最後の「どちらも、不明な点は…」が、別の節の中で何を指すのか分からなくなった。ペア判定（片方向のみ）は「内容の絞り込み」で候補版が2勝1敗、「分けすぎでない」で旧版が3勝だった。
- つまり、候補の規則は、書き換えを許すモード B でも、見出しを足す方向には動かなかった。動いた1件も、規則の例示と同じ形の入力だった。
- 旧版も、混在した節を分けない。ただし、原文のまま返すことが多く、壊してもいない。

## 解釈と限界

- 「見出しの下を一つの話題にする」という考え方自体は、先行研究と整合する。ただし、この比較は、その規則を足して LLM の出力が良くなることを示せなかった。それだけで、考え方が間違っているとは言えない。
- モード B（「意味を保つ範囲での書き換え」）で、利用者が頼んでいない見出しの追加・分割まで行うのが望ましいかは、別の判断である。この実験は、それを望ましい挙動として固定していない。
- 自作11ケース、同じモデル系統の採点、人間の採点なし、3反復は独立ではない。未使用文書での一般化と、人間の読者の理解度は、未計測。
- 判定の欠落は、記録を残したまま終えた（再実行しない決まり）。指標3は、実施できなかったため、この結果を採否の根拠にしていない。採否は、指標1・2の未達で決まる。
- API 換算の費用は約5米ドル（記録の `cost_usd` の合計）。
