# 意味確認の改良で見つかった懸念の検討・再検証

v0.21.0の結果を出発点に、今回の対象Issueを解消するまで検討・修正・再検証する。既存の別案件は対象に含めない。

## 対象と判断

| Issue | 懸念 | 対応 |

## 検討の経緯

前回は複数ケースを一つの文脈で確認していた。今回はケースを独立した文脈へ分ける。単独での旧新版比較では再現しない懸念を、修正による改善と断定しない。

最初の補修をClaudeで確認したところ、解決しない制約変更を、但し書き付きで質問する出力が残った。また、本文のみの例で比較関係を一つに決める出力が出たため、#113を追加した。これらを成功扱いにせず、指示を補修した。[最初の実行記録](meaning-concern-run.json)に実出力と欠測を残す。追加例1件の呼び出しは失敗し、出力を取得できなかった。

入力を16例へ増やすと最初の12例のハッシュと一致しなくなるため、#114を追加した。[Claudeへ与えた12例](meaning-concern-claude-cases.json)を分け、記録の元のハッシュとの一致を確認した。途中の指示は[基準からの差分](meaning-concern-claude-instructions.patch)から再構成し、3ファイルのハッシュを照合できるようにした。最初の実出力と失敗は変更していない。

評価経路を変えるにあたり、別モデルの結果を旧モデルの結果と混ぜない。旧版・補修後を同じ条件へそろえ直して比較する。通常の利用者設定を引き継ぐ予備確認では、文案の外に作業注記が出たため、利用者設定を読み込まない隔離実行へ切り替える。予備確認を最終結果へ置き換えず、条件の違いを残す。

## 評価入力と実行条件

- [人工16ケース](meaning-concern-cases.json)。m01–m08は前回の例、n01–n04は今回の開発例、h01–h04は最後の補修後、Codexで実行する前に固定した追加例。
- Claudeの最初の比較は、各ケースを独立して実行。実行モデルは`claude-sonnet-5-5`。既存の`tools/evaluate_readability.py:invoke`で3ファイル全体を指示として渡した。モデルへのツールは無効。
- 最終比較は、旧版`46cd26c`と補修後をCodex CLIで同条件にする。`--ignore-user-config`、`--ephemeral`、`--skip-git-repo-check`、`--sandbox read-only`を使う。要求するモデルは`gpt-6.1-sol`、推論設定は`medium`。実際に提供されたモデルの識別子はCLIのイベントから取得できない。
- 指示は`SKILL.md`全文、`readability-rules.md`の第4節、`examples.md`の第29節以降。各版で同じ箇所を読み込ませ、対象外の詳細を評価へ混ぜない。各ケースを別プロセスで1回ずつ実行する。m01の回答後は、最初の入力と応答・利用者の回答を再提示する。
- 全出力と指示のハッシュ、フラグ、使用量、実行失敗を[最終比較記録](meaning-concern-codex-run.json)に残す。ツール実行のイベントが出た場合は、ツールなしの確認として成功扱いにしない。
- 意味と質問の必要性は実装者が原文・条件と照合する。文全体の完全一致、疑問符の数、指示のキーワードの有無だけを合否基準にしない。

## 結果

最終比較は、新旧それぞれ16例とm01の回答後の応答を取得できた。ツール実行のイベントはなかった。実装者が原文・条件と照合し、別の新しい文脈でも版名を隠して[モデル判定](meaning-concern-grading.json)を行った。新旧32件の最初の応答は、この人工例の判定条件をいずれも満たした。モデル判定も32件pass、fail・uncertainは0件だった。同じ要求モデルを使った別文脈の判定であり、異なるモデルによる独立性や人手の確認を示すものではない。

| Issue | 最終出力・確認結果 | 判断 |
|---|---|---|
| #109 | m01・n01・h01は比較対象の関係だけを質問。周囲の報告先・確認対象・個々の店などを質問しない。m02・m08は質問しない | この例で解消条件を確認 |
| #110 | m06・n02・h02は字数上限だけを質問。n04は文数の矛盾だけを確認し、有効な二つの調整案を示す。未計数の字数目安を示さない | この例で解消条件を確認 |
| #111 | m07・n03・h03は担当を明示し、m08は未知の主体を補わない | 単独で使う案と、不明な主体の対照を確認 |
| #112 | 開発文書に対象Issue・解消条件・反復・欠測の扱い・リリースと後片付けを記載し、今回の6件と結果を照合 | 手順と今回の適用を確認 |
| #113 | m04・h04は未確定の比較語句を残し、周囲だけを修正。質問や注記を付けない。m05は意図的な読みを保持 | この例で解消条件を確認 |
| #114 | 最初の12例の元のハッシュ、途中の3指示のハッシュ、最終16例と最終指示のハッシュを照合 | 実行記録から入力と指示を再現できることを確認 |

このCodex比較では、旧版も同じ判定条件を満たした。したがって、改善率や旧版より優れることは示していない。Claudeで観察した途中の失敗に対応する指示を補ったことと、利用可能な別経路で最終の条件を満たしたことを区別する。最終指示でのClaude再実行はできておらず、Claudeでの再現率が改善したとは述べない。

## 構造・配布・導入の確認

公開対象だけのソースで全体検証と配布物・隔離した導入先の確認を行う。既存の未コミットの説明文と、非公開フィードバックは公開対象へ含めない。

`tools/check_all.py`は公開対象だけの最終ソースで成功し、1,025件中1,012件成功・13件スキップだった。版のサンプルを同期し、入口文書の175行上限は変えていない。ZIPの整合性、SHA-256、共通の指示・規則・例・版の内容一致を確認した。

隔離した配置先へv0.21.0を導入し、v0.21.1へ更新して、正本との厳密比較と同梱スクリプトの実行を確認した。Codex共通、Claude Code、Antigravity IDE、Antigravity CLIの4配置先を削除し、対象Skillが残らないことを確認した。利用者の既存コピーは更新していない。これらは導入経路の検証であり、各製品のモデル挙動の検証ではない。

公開差分は、非公開報告票の原文・結果との24文字連続一致と固有語を確認し、人工例だけであることも目視で点検した。途中の指示の差分は`git apply --unidiff-zero`で基準に適用し、元の3ファイルのハッシュと一致することを確認した。

## 限界

人工例の各1回の確認であり、一般的な成功率や未使用の実文書での効果は測らない。最後の追加例を見た後に指示を変える場合は、その例も開発に使用済みとして扱い、追加の確認例を分ける。製品固有のインストール済みSkillの実呼び出し、Windows実機、独立した人手判定は別の検証であり、構造検査やプロンプトを渡す実行で確認済みとはしない。
