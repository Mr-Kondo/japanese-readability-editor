## 採点点検と不一致

採点の2軸は、意味保持と課題達成です。
実出力30件に、事前に期待値を決めた採点点検5件を混ぜ、無作為な順序で3組に分けた。
独立採点は全35件を返し、欠測や重複はなかった。
期待値は独立採点へ渡していない。

点検は5件中4件で両軸が一致し、軸別では10判定中9判定が一致した。
p05 の「確認済みの無料対象を再質問する候補」で、課題達成の fail は一致した。
意味保持は、事前期待値が pass、独立採点が fail となった。
事前基準は誤断定のない質問を意味保持 pass とするが、採点者は既知の意味を疑問視する点も違反とした。
元ケースの禁止事項は意味保持と課題達成を区別せず、期待値側の定義に不備があった可能性もある。
採点者の誤りとは断定しない。期待値を書き換えて合格にせず、事前条件どおり独立採点を採否に使わない。

実出力では次の5件で判定が分かれた。
以下は原因調査用であり、確定した合否やスキルの成績ではない。

| 出力       | Codex（意味／課題） | 独立採点（意味／課題） | 相違点                                                                             |
| ---------- | ------------------- | ---------------------- | ---------------------------------------------------------------------------------- |
| t02・1回目 | fail / pass         | pass / pass            | 新しい展示ケースは明確だが、資料が既存という背景情報の省略を意味保持違反とするか   |
| t04・3回目 | pass / pass         | fail / fail            | 「平日のみ」から祝日の利用不可まで述べることを、語義の展開とするか条件追加とするか |
| u01・2回目 | pass / pass         | uncertain / uncertain  | 未確定の読みを条件付きで示す長い応答の、意味保持と必要性                           |
| u03・2回目 | pass / fail         | uncertain / pass       | 従量プランの利用回数を尋ねない点と、仮の比較文が料金構造を仮定する点               |
| u03・3回目 | pass / fail         | pass / uncertain       | 従量プランの利用回数や上限も、明示的に確認すべきか                                 |

Codex の暫定判定は、意味保持が29/30、課題達成が28/30で pass だった。
独立採点の暫定判定は、両軸とも pass が27/30、fail が1/30、uncertain が2/30だった。
意味保持の uncertain は u01・2回目と u03・2回目、課題達成の uncertain は u01・2回目と u03・3回目です。
両軸の fail は t04・3回目です。全30出力について各軸を個別に数え、採点点検5件は除外した。
Codex の集計は初回判定欄の集計であり、レビュー後も未確定の t04・3回目の pass を含む。
集計の一致は出力ごとの判定の一致ではない。
点検不合格と不一致があるため、これらを確定した成功率として報告しない。

モード C の3出力は、改行を除いた文字列が原文と一致し、全件に段落区切りがあった。
空白や句読点まで削除して比べる方法は使っていない。
これは文言保持の機械的な確認であり、読みやすさの効果測定ではない。

## 判断と機会費用

修飾先の確定と比較対象への数値の対応は、生成例で確認できた。
一方、意味の補作を避けながら何を確認するかについては、採点の境界が十分に定まっていなかった。
特に u03 は確認不足が2回疑われるが、二者で合否が一致せず、規則不足の確認には至っていない。
Codex の判定だけなら3回中2回の失敗という修正条件に該当するが、採点が確定していないため保留する。
t04・3回目も、禁止事項を広く適用すれば条件追加となり、Codex の見落としの可能性がある。
u01・2回目は、条件付きの読みの提示と期限文の言い換えを Codex は許容した。
ただし、その長さや補足の必要性には不一致が残るため、確定した pass にはしない。
現行の規則には、比較対象ごとの特徴が不明なら必要な点だけ確認する指示が既にある。
この状態で似た指示を追加すると、採点の不確かさへ過剰適合するおそれがある。

したがって参照規則と修正例を増やさず、候補版の生成も行わなかった。
版、配布物、Mac の導入先は更新していない。今回は版の更新がなく、導入先の更新も非該当です。
確認できていない改修のために、追加の生成・採点費用と規則の維持費を払うことは避けた。

再開する場合の優先順位は次のとおりです。今回の範囲では実施しない。

1. 質問の意味保持と課題達成を区別する採点基準を、人の判断で確定する。
2. 背景情報の省略、平日と祝日の扱い、比較で必要な確認事項をケースごとに明記する。
3. 改訂した計画を再レビューした後、別の未使用例で現行版を調べる。
4. 規則不足が確認できた場合だけ、最小修正と同条件の比較へ進む。

## 保存と限界

公開する変更は、計画、自作ケース、この結果と評価一覧への案内に限る。
生の生成・採点・レビューは Git 管理外の `feedback/jaist-ambiguity/` に残す。
再確認のために実行用の一時スクリプトも `feedback/jaist-ambiguity-run.py` に残す。
既存の変更や未追跡ファイルは、この評価の変更へ含めない。

人による採点、実利用、Claude Code 以外の生成、導入済みスキルの自動読み込みは未検証です。
自作10例であり、モード A/C は各1例だけです。複雑な資料や未使用文書への一般化は判断できない。
スキルなしとの比較もなく、生成の成功をスキル固有の効果とは扱えない。
採点の不一致をモデルの多数決で解消しない。
Codex の初回記録では、大半の判定理由が定型文で、個別の根拠という計画要件を満たしていなかった。
初回記録を保持し、結果レビュー後に出力ごとの理由を補った。初回採点の品質上の限界として残す。
最終レビューは提示資料の確認であり、レビュワー自身によるテスト・ハッシュ・実ファイルの再検証ではない。
