# 独立した話題を並べた見出しを、本文が別々なら分ける規則の評価(#174)の計画

実行の前に固定する計画。結果は `evals/heading-split-result.md` に記録する。この計画は、結果を見てから変えない。変えるときは、理由と日付を残し、変更前の結果を残したまま、新しい記録として実行し直す。

きっかけは、利用者の指摘である。「○と△について」の見出しの下に、○と△が入り混じった文章があると読みづらい。「○について」「△について」と見出しを分けるほうが読みやすい。「○と△の関係について」のように曖昧な語がつく見出しは、節の冒頭の文で中身を言い切るのがよい。方針は [Issue #174](https://github.com/Mr-Kondo/japanese-readability-editor/issues/174) に書いた。現行の「見出し」の規則は、ラベルだけの見出しを具体化するもので、話題を並べた見出しを扱わない。

規則の追加は、旧版と新版を同じ評価で比べてから決める。この回は、その比較である。

## 比べる版

- 旧版(base): コミット `82d81ad2fb1c9ea853c7890fba2d803f9c8691fe` の `SKILL.md`、`references/readability-rules.md`、`assets/examples.md`。
- 新版(cand): この計画をコミットした次のコミットで、同じ3ファイルを次のように変えたもの。計画のあとに書き、評価の結果を見て調整しない。
  - `readability-rules.md` の「見出し」の節に、複数の話題を並べた見出しの扱いを足す(Issue #174 の合意の5点)。
  - `SKILL.md` の見出しの項目(79行目)に、同じ内容の短い節を足す。SKILL.md は行数ガードの上限(175行)にあるので、行は足さない。
  - `examples.md` に例34を足す。別話題を分ける例と、比較なので分けない例を1組で載せる。評価の9本とは別の文章で作る。

## 問い

1. 旧版は、本文が別々の話題の見出し(「AとBについて」)を、すでに分けるか。分けるなら、規則を足す価値は小さい。
2. 新版は、分けるべき見出しを分け、分けてはいけない見出しを分けないか。意味・数値・条件を保つか。

## 入力

[heading-split-run/cases.json](heading-split-run/cases.json) の9本。自作の短い文書で、依頼は次のとおり。出力は本文だけを返させる(変更報告は返らない)。

| id | 群 | 内容 | 期待 |
|---|---|---|---|
| h01 | split | 本文が「ログ」「設定」の順に並んでいる | 分ける |
| h02 | split | 番号つきの見出し(「2. 打刻と休暇申請について」)で、後ろに「3. 問い合わせ」がある | 分け、番号を振り直す |
| h03 | split | 「予約」「キャンセル」の文が1段落に入り混じっている | 分け、話題ごとにまとめる |
| h04 | keep_body | 有料プランと無料プランの違い | 分けない |
| h05 | keep_body | CSV と JSON の使い分け | 分けない |
| h06 | keep_body | 「検索と置換」を1つのダイアログとして説明 | 分けない |
| h07 | request | 「見出しの文言は変えないでください」の指定つき | 見出しを変えない |
| h08 | request | 「モード C。段落だけ分けてください。」 | 見出しも文字も変えない |
| h09 | vague | 「親ジョブと子ジョブの関係について」。本文の冒頭が「ここでは…を説明する」 | 分けない。冒頭の文で関係を言い切る |

各本を、旧版・新版の両方で3回ずつ生成する(54出力)。モデルは `sonnet`、推論は `medium`、ツールと別スキルは無効(#167、#57 E と同じ呼び出し)。生成側には、request・context・text とスキル3ファイルだけを渡す。keep・topics は渡さない。

## 数え方(生成の前に固定する)

- 見出し: 出力の Markdown の見出し行(`#` で始まる行)。
- 状態: 各入力の話題2語(topics)を使い、出力の見出しを機械的に分類する。
  - 分けた: 2語がそれぞれ別の見出しにあり、両方を含む見出しがない。
  - 残した: 両方を含む見出しがあり、別々の見出しがない。
  - その他: 上のどちらでもない。全件を人が読む。
- 見出しが変わらない: 出力の見出しの並びが、入力と同じ(h07、h08)。
- 文字が変わらない: 空白と改行を除いて、出力が入力と同じ(h08)。
- 番号: h02 の出力で、見出しの番号が 1 から連続している。
- 保つ語の欠落: 各入力で固定した語(数値・条件・用語)が、出力に現れない。機械的に数える。
- 人が読む: 「分けた」出力(split 群)と h09 の全出力を、原文と並べて読む。意味・数値・条件・例外の変化を、引用つきで記録する。h09 は、見出しの直後の文が「関係」の中身を言い切っているかも、旧版・新版で記録する。この判断は主観を含む。採否には使わない。

## 採否の基準(事前に決める)

新版を**採用候補**とするのは、次の6つをすべて満たすときである。

1. split 群の9出力のうち、新版で「分けた」が8以上で、旧版より多い。
2. h02 の「分けた」出力で、番号が連続している(新版)。
3. keep_body 群の9出力で、新版の「分けた」が0。
4. request 群で、新版の見出しがすべて変わらない(h07、h08 の6出力)。h08 は文字も変わらない。
5. h09 の3出力で、新版の「分けた」が0。
6. 新版の27出力(9本×3回)の全部で、保つ語の欠落が0。かつ、人が読んだ split 群・h09 で、意味・数値・条件の変化が0件。

満たさないとき、または旧版がすでに split 群の8以上で「分けた」とき(基準1の「旧版より多い」を満たさないとき)は、規則を入れない。旧版が分けている場合は、規則が不要だった可能性として記録する。満たさない基準があり、規則を絞れば直せそうなら、その理由を書く。ただし、この記録の中で新版を調整して再判定しない。調整は、新しい版・新しい記録として、別に実行する。

旧版・新版の件数は、そのまま並べる。確率や一般化は主張しない。

## 費用の上限

全体で5ドル。超える見込みになったら、止めて報告する。54出力の見込みは約3.6ドルだが、これは #57 E の30出力(1.99ドル)からの推定で、測っていない。

## 実行の手順

1. この計画、cases.json、runner.py をコミットする(生成前)。
2. 新版の3ファイルを書き、別のコミットにする。
3. `runner.py` で準備し(ハッシュと両版の全文を run.json に保存)、コミットする。
4. `runner.py --generate`、`--count` の順に実行する。
5. 結果を `evals/heading-split-result.md` に書く。

## 限界

- 下書きは合成した9本の短い文書で、実文書での頻度や効果を表さない。
- 3回の反復は、独立した27種類の文章ではない。
- 「分けた」の判定は、見出しに話題の語が入っているかによる。語の言い換えは「その他」になり、人が読む。
- 出力は本文だけで、変更報告は返らない。「直さずに報告する」(h07、h08、判断がつかない1組の語)と、番号の振り直しで壊れる参照の報告は、測れない。h02 には、参照を入れていない。
- 意味保持の判断は、人(実行者)が読んで決める。別の採点者による盲検の採点はしない。
- モデルは `sonnet`(medium)の1つだけ。ツールを使えない条件で、スクリプトによる照合を含まない。
- 実利用での効果の確認は、この評価と分ける。
