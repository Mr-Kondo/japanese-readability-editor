# スキルなしとの比較評価（#165）の計画

実行の前に固定する計画。結果は [no-skill-comparison-result.md](no-skill-comparison-result.md) に記録する。この計画は、結果を見てから変えない。変えるときは、変更の理由と日付を残し、変更前の結果を残したまま、新しい記録として実行し直す。

## 問い

現行スキルは、スキルなし、および数行の指示と比べて、何に効くか。意味の保持、読みやすさ、費用を、同じ入力と同じモデルで測る。

きっかけは、参考先 nanaism/yomiyasu の v3.0.0 の公表（追跡 #164）である。上流の数値は、こちらの結果の根拠にしない。こちらのスキルで同じことが言えるかは、この評価で確かめる。

## 群

| 群 | 内容 |
|---|---|
| none（スキルなし） | 依頼だけを渡す。スキルの本文も、指示も渡さない |
| short（数行の指示） | `README.md` 全文と `SKILL.md` の description だけを読んだ新しい文脈のモデルが書いた、5行以内の指示。書かせた文を、そのまま保存して固定する。実行者は書き直さない |
| skill（現行スキル） | `SKILL.md`、`references/readability-rules.md`、`assets/examples.md` の本文を、既存の評価と同じ方法でプロンプトに入れる |

- 入力は [readability-cases.json](readability-cases.json) の12ケース。各群で、1ケース3回、36出力を生成する。
- none と short には、依頼の先頭の「モード A。」「モード B。」を外した文を渡す。スキルを知らない利用者は、モードを指定しないため。外すのはこの接頭辞だけで、残りの依頼文は変えない。skill には、元の依頼をそのまま渡す。
- モデルは `sonnet`、推論は `medium`。ツールと別スキルを無効にした、プロンプトの評価である。製品でのスキルの起動・検出は検証しない。
- 各呼び出しは新しい文脈で、1ケースずつ生成する。採点も別の文脈で行う。
- 実モデルの識別子が、生成と採点のすべてで一致しなければ、結果を有効にしない。

## 採点

1. **意味保持**: 全出力（108）を、版名と群名を伏せ、順序を無作為にして、既存の採点指示（pass / fail / uncertain）で判定する。採点の信頼性の確認として、[readability-generalization-cases.json](readability-generalization-cases.json) の点検用12項目（期待: fail 8、pass 4）を混ぜ、全問が期待どおりでなければ、結果を有効にしない。
2. **読みやすさ**: skill と none、skill と short の、同じケース・同じ回の組で、両方の意味保持が pass の組だけを比べる。左右は無作為にし、左右を入れ替えて2回判定する。2回の判定が一致した場合だけ勝敗とし、割れたら uncertain にする。判定は left / right / tie / uncertain。短さ、変更量だけでは決めない。
3. **補助の数**: 費用（群ごとの合計）、依頼された推敲で原文を空白を除いて同一のまま返した出力の数（原文のあるケースだけ）。

## 読み方（事前に決める）

- **意味保持で優位**: skill の fail の数が none と short の両方より少なく、skill の fail と uncertain の合計が両方以下。
- **読みやすさで優位**: skill 対 none と skill 対 short の両方で、skill の勝ちが負けより多い。
- どちらも満たさない項目は、「優位とは言えない」と書く。差の大小は、件数をそのまま並べる。統計的な有意差は主張しない。
- 結果が「意味保持で優位、読みやすさで優位とは言えない」なら、README と `docs/design.md` に、その範囲を書く。それ以外の結果でも、測った範囲を超える書き方がないかを確かめる。
- この Issue では、スキルの規則を変えない。規則の変更が必要になったら、別の Issue にする。

## 有効にする条件

実モデルの一致、欠落なし（生成108、採点・比較の呼び出しがすべて形式どおり）、点検12項目の全問正答、short の指示が生成前に固定されていること。どれかを満たさなければ、読み方の判定は出さず、HOLD とする。

## 費用の上限

全体で10ドル。超える見込みになったら、止めて報告する。

## 限界

- 入力の12ケースは短い自作文（26〜66字）で、意味の落とし穴を狙った作りである。実際の文書に近い長さではない。読みやすさの差は、同点が多くなる見込み。実文書での比較は、#38〜#44 の公開文書の評価に任せる。
- 採点は、生成と同じ系統のモデルで、人の判断に校正していない。「モデル採点では」と限定して書く。
- 3回の反復は独立した36種類の文章ではない。短い指示（short）は、1つの指示の1回の書き出しであり、書き方を変えた指示では結果が変わりうる。
- 実利用での効果（人の読解時間、理解度）は測らない。

## 実行中の逸脱の記録

- 2026-11-12: short の指示の最初の出力は、前置き1行と番号つきの5項目で、合わせて6行だった。「5行以内」の条件を1行超えた。出力を生成する前に、再生成せず、この出力をそのまま採用すると決めた。再生成は書き出しの引き直しになり、実行者の選択が入るため。「短い指示」という趣旨（約600字）は満たすと判断した。この逸脱は、結果文書にも書く。採用した文は、`evals/no-skill-run/run.json` の `short_instruction` にある。
