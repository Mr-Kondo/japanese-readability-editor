# 比較情報の確認と短い質問の追加評価

[Issue #216](https://github.com/Mr-Kondo/japanese-readability-editor/issues/216) の追加評価です。
[初回の保留結果](jaist-ambiguity-result.md)は変更せず、採点基準を明確にして新しく実行する。
対象は、比較に必要な情報の確認漏れと、単純な確認への長い説明です。

## 仮説と変更の範囲

比較の各対象に必要な特徴を対応づけて尋ねる例と、回答に不要な仮案を省く指示で改善できるか調べる。
候補は参照規則の短い補足と修正例1節までとする。実装前に失敗と変更案を独立レビューする。
新しい処理、依存、モード、確認項目の一律追加は行わない。
既存の意味確認・本文のみ・意図した曖昧さの保持を優先する。

実行時ファイルの候補は `references/readability-rules.md` と `assets/examples.md` だけです。
採用時は版と関連する配布情報を確認し、この Mac の既存導入先へ反映する。
不採用なら実行時ファイルは現行版へ戻し、実験資料だけ残す。
外部への公開、push、PR、マージ、リリースは、今回の実験の許可には含めない。

## ケースと採点の固定

[新しい自作10ケース](jaist-ambiguity2-cases.json)を、各版で3回ずつ独立して生成する。
q01〜q04 は確認が必要な対象、c01〜c06 は確認済み、本文のみ、意図した曖昧さ、部分的な既知情報などの対照です。
全ケースの形式と採点軸を生成前に固定し、旧30出力と合算しない。
人が採点した正解とは扱わない。

意味保持と課題達成を分ける。

- 意味保持: 出力内で断定した事実が資料と矛盾せず、未知の料金・上限・修飾先などを確定していないか。
- 完成稿を出す場合は、ケースの `preserve` に明記した必要な事実も残す。背景情報の全転載は要求しない。
- 質問だけの応答は、誤った事実の断定がなければ意味保持 pass とする。既知情報への質問、質問不足、本文未提出は課題達成で判定する。
- 条件付きの案は未知の事実の断定とは区別する。q03・q04 でも条件を明示した仮案は許容し、未確定の完成稿と区別する。ただし、答えるために不要な案も含めて全文の長さを測る。
- 課題達成: `success` に書いた、必要な確認事項、既知情報の保持、指定された出力形式を満たすか。
- 意味上の解釈が割れる場合は uncertain とする。解消しなければ保守側で残し、採用しない。

各出力を Codex と Claude Code が全件確認し、軸別に pass / fail / uncertain、引用と個別の理由を記録する。
独立採点へ版名と Codex の判定を渡さず、順序を無作為化する。
候補版を作った場合は両版を混ぜて独立採点する。Codex は版を知るため、完全な二重盲検とは扱わない。
採点点検7件の期待値は隠し、両軸14判定すべての一致を要求する。
質問の意味保持と課題達成を分ける点検を含む。
不一致なら期待値を後から変えて通さず、理由を調べて保留する。

q01〜q04 は質問の応答全体の文字数も測る。前後の空白だけを除き、改行と注記も1文字として数える。
各出力は180文字以下を目標とする。採点者にこの数値を渡さず、機械的に集計する。
この上限は今回の単純な4ケースの評価値であり、実行時の一般規則にはしない。
180文字と40%減は、短い質問に比べて説明が長い出力を選別するための探索上の判断値です。
読みやすさの実証値ではなく、別の閾値なら採否が変わりうる恣意性を限界として残す。
c06 の複数の不明点など、必要な質問を長さのために削ることは認めない。

## 失敗確認と採用条件

まず現行版だけを30回実行する。
次のいずれも起きなければ、変更せず終了する。

- q01〜q04 の180文字超が12出力中3件以上ある。
- 同じ対象ケースで、必要な確認事項の欠落が3回中2回以上あり、独立レビューでも確認できる。

欠落は `success` の各対象と特徴の組み合わせごとに確認する。対象1ケースでも条件を満たせば失敗確認とする。
Codex と独立レビュワーが引用を確認し、不一致なら確認漏れによる失敗とは確定しない。
文字数だけの条件は機械的に判定し、独立レビューでも出力と算出方法を確認する。

失敗の出力、規則との対応、最小修正案を実装前にレビューする。
追加例の候補は、配送方法ごとの送料と受取日の確認です。評価例と比較の構造は近いため、未使用事例への転用は未確認とする。
既存の失敗を隠したり、正常な実装を壊したりして Red を作らない。
候補は1回だけ実装し、同じ入力と条件で30回生成する。
採用には以下をすべて必要とする。

- 候補版は全30出力で意味保持と課題達成が二者とも pass。uncertain や未解決の判定不一致は0件。
- 候補版の対象12出力はすべて180文字以下。
- 対象12出力の文字数の中央値が現行版より40%以上小さい。
- 事前の採点点検が全判定で一致し、対象の必要事項と対照の振る舞いを損なわない。
- モデル・条件が一致し、未解決の重大なレビュー指摘がない。
- 追加例にケースの文、固有名、数値を転載しない。比較という構造は共有するため、過適合の可能性は残る。

数値はこの探索の採否基準であり、統計的な改善や実利用の効果の証明ではない。
機能の回帰や基準未達なら候補を不採用にする。条件を緩めて採用しない。
全30出力を要求するのは、短縮のために意味や対照を損なう候補を採用しないためです。
厳しい条件で小さな改善を見送る可能性を許容する。不採用なら追加候補を作らず終了する。

## 実行条件と資源上限

初回と同じ既存の `tools/evaluate_readability.py` の `invoke`、`prepare` を再利用する。
旧実験のローカル実行スクリプトの生成処理を呼び、出力先・計画・ケースだけを差し替える。
生成入力は3つのスキル本文と request/context/text だけとし、採点情報を含めない。
共通指示は初回と同じ、REQUEST の指定に従う指示です。全件を本文のみに強制しない。
CLI は sonnet、effort medium、ツールなし。実行モデル識別子、CLI版、引数、入力と実行コードのハッシュを残す。
入力スキルは各版の開始時に凍結する。実行中の編集を反映しない。
旧生成処理のハッシュに加え、開始時に計算したラッパーのハッシュも通常終了・例外中断時に保存する。強制終了など、保存できない中断では記録の欠落を報告する。

生成は各版30呼び出し、同時最大3件、単一180秒のタイムアウトです。
各版20分を新規送信の期限とし、送信済み最大3件は既存のタイムアウトまで回収する。
費用は3件ごとに確認し、記録上の API 換算20米ドル超、欠測、エラー、利用制限、モデル不一致で中断する。
追加請求額とは区別する。途中終了は原因調査だけに使い、採否に使わない。
1件10〜60秒なら2〜12分程度を見込むが、遅延は保証できない。
旧新版でモデル識別子、CLI版、effort、共通指示、ケース、実行処理が違えば比較を成立したと扱わない。
CLIで固定できないサンプリング条件は不明として残す。
既存の保存先へ再実行せず、出力の無条件な再取得もしない。

## 完了と限界

計画・ケース、失敗と修正案、実装・結果の各段階を Claude Code または Antigravity が確認する。
テスト、Markdown の整形・文法・日本語校正、必要な版と導入先の確認を実施する。
詳細出力は Git 管理外の `feedback/jaist-ambiguity2/` に残し、公開対象へ含めない。
既存の無関係な変更と初回の記録を保持する。

スキルなしとの比較、実利用、人の採点、導入済みスキルの自動読み込みは検査しない。
同じ自作ケースを修正根拠と比較に使うため、未使用文書への一般化は示さない。
既存3環境の構成、frontmatter、参照の分け方、更新方法は初回の調査を引き継ぐ。
新しい環境機能や配布方法は追加しない。細かな規則を増やす維持費と、追加生成・採点の費用を採否時に確認する。
質問と本文を併用する必要がある複雑な文や、複数ターンで回答済みの内容を聞き直す挙動は検査しない。
